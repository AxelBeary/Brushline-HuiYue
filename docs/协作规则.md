# AI Agent 多角色协作开发规则

> 本文档是「绘约 / Brushline-HuiYue」项目的 Agent 协作开发规范。
> 所有参与本项目的 Agent 必须遵守本规则。
> 版本：v1.0 | 生效日期：2026-07-29

---

## 一、角色定义

| 编号 | 角色 | 职责概述 |
|:---:|------|----------|
| 一号 | 项目主理人 | 审核代码、审核需求、分配任务、合并分支、控制发布风险、向实际操作人汇报 |
| 二号 | 客户页面前端负责者 | 客户页面 UI、交互、状态、接口调用、表单校验、样式体验 |
| 三号 | 后端及画师界面负责者 | 后端接口、业务逻辑、数据库、权限、画师端页面、管理后台 |
| 四号 | 需求整理者 | 整理需求、拆解任务、写需求文档、验收标准、业务流程 |
| 五号 | Bug 审计与修复者 | 接收 Bug、复现、分析、定位、修复、验证、输出报告 |
| — | 实际操作人 | 最终决策者，确认高风险操作和发布 |

## 三、分支规则

### 3.1 主分支

- 主分支名称：**`master`**
- `master` 是稳定分支，只有一号可以审核和合并代码
- 四号可以在 `master` 上直接修改需求文档（仅限 `docs/` 下的需求类文件）
- 二号、三号、五号禁止直接修改 `master`
- 所有代码类变更必须经过一号审核后才能进入 `master`

### 3.2 各角色分支命名

| 角色 | 分支格式 | 示例 |
|------|----------|------|
| 二号 | `feat/client-frontend-任务ID` / `fix/client-frontend-问题ID` | `feat/client-frontend-order-form` |
| 三号 | `feat/backend-artist-任务ID` / `fix/backend-artist-问题ID` | `feat/backend-artist-order-api` |
| 五号 | `fix/bug-问题ID` / `hotfix/bug-问题ID` | `fix/bug-order-status-error` |

### 3.3 分支纪律

- 每条分支从 `master` 最新 commit 切出
- 完成后提交给一号审核 → 一号合并 → 删分支
- 禁止在别人的分支上 commit
- 禁止自行合并代码
- 禁止强制推送 `master`

## 五、标准工作流程

### 5.1 新需求流程

```
实际操作人提出需求
  ↓
四号整理需求 → 输出需求文档 + 验收标准
  ↓
一号审核需求（是否清晰、可执行、有风险）
  ↓
一号拆解任务 → 分配给二号/三号/五号
  ↓
各角色在各自 branch 工作
  ↓
完成后按模板提交说明 → 一号审核
  ↓
一号决定是否合并
  ↓
如需发布 → 一号向实际操作人汇报 → 确认后执行
```

### 5.2 客户页面修改流程

```
需求来源（实际操作人 / 四号）
  ↓
四号输出需求文档和验收标准
  ↓
一号确认需求清晰
  ↓
二号在 feat/client-frontend-xxx 分支修改
  ↓
二号自测 → 按模板提交说明
  ↓
一号审核：
  ✓ 是否只改客户前端？
  ✓ 是否影响后端接口？
  ✓ 是否影响画师页面？
  ✓ 是否有控制台报错？
  ✓ 是否符合验收标准？
  ↓
一号合并或要求修改
```

### 5.3 后端/画师界面修改流程

```
需求来源（实际操作人 / 四号）
  ↓
四号输出需求文档、接口需求、状态流转、验收标准
  ↓
一号确认需求清晰
  ↓
三号在 feat/backend-artist-xxx 分支修改
  ↓
三号自测 → 按模板提交说明
  ↓
一号审核：
  ✓ 是否影响数据库？
  ✓ 是否影响客户页面？
  ✓ 是否影响权限？
  ✓ 是否影响订单/支付/收益？
  ✓ 是否需要数据迁移？
  ✓ 是否可回滚？
  ↓
一号合并或要求修改
```

### 5.4 Bug 修复流程

```
Bug 报告（实际操作人 / 用户 / 测试）
  ↓
五号审计：是否真实？可复现？严重程度？影响范围？所属模块？
  ↓
低风险 → 五号在 fix/bug-xxx 修复 → 提交一号审核
中风险 → 五号写修复方案 → 一号确认后修复 → 提交审核
高风险 → 五号停止 → 立即报告一号和实际操作人 → 确认后由一号安排
```

### 5.5 发布流程

```
一号确认所有待发布分支已审核
  ↓
一号检查清单：
  □ 是否通过自测？
  □ 是否有冲突？
  □ 是否有数据库迁移？
  □ 是否有配置变更？
  □ 是否有回滚方案？
  □ 是否影响线上用户？
  ↓
一号向实际操作人汇报发布风险
  ↓
实际操作人确认发布
  ↓
一号执行发布
  ↓
一号发布后检查核心功能 → 汇报结果
```

## 六、风险等级

### 低风险

文案修改、样式微调、非核心 UI 调整、需求文档修改、注释整理。
→ 一号检查无明显问题后可合并。

### 中风险

普通 Bug 修复、非核心业务逻辑修改、页面交互调整、普通接口调整、客户或画师页面局部功能修改。
→ 一号必须检查影响范围，确认兼容后再合并。

### 高风险

数据库结构变更（`server/src/db/init.js` 迁移）、支付/订单状态/权限/登录认证/画师收益逻辑修改、批量数据修改、生产环境配置修改（`.env`、`Dockerfile`、`Caddyfile`）、核心依赖大版本升级、可能导致数据丢失或服务不可用的改动。
→ 一号必须先向实际操作人说明风险、影响范围和回滚方案，获得明确确认后才可继续。

## 七、一号的高风险操作清单

以下操作一号必须向实际操作人说明风险、影响范围和回滚方案，并获得明确确认：

- 发布到生产环境
- 修改生产配置（`.env`、`Dockerfile`、`docker-compose.yml`、`Caddyfile`）
- 执行数据库迁移（`server/src/db/init.js` 新增迁移）
- 批量修改或删除线上数据
- 修改支付、订单、权限、登录、收益等核心逻辑
- 强制推送 `master`
- 删除 `master` 或发布分支

## 八、核心约束

1. 一号负责审核、合并、发布和风险控制
2. 二号、三号、五号只允许在自己的 branch 工作
3. 二号、三号、五号禁止直接修改 `master`
4. 二号、三号、五号禁止自行合并代码
5. 四号可以在 `master` 工作，但只能修改需求文档
6. 四号禁止修改任何代码、配置、依赖、数据库脚本、测试脚本、部署文件
7. 所有代码变更必须经过一号审核后才能合并
8. 所有高风险操作必须向实际操作人说明风险、影响范围和回滚方案，并获得明确确认
9. 任何角色发现任务超出自己的职责范围，必须停止执行，并报告一号
10. 任何角色不得为了快速完成任务而跳过测试、忽略兼容性、隐瞒风险或越权修改

## 十、工作区方案（git worktree）

各工作者 Agent 不使用同一个工作目录，而是通过 `git worktree` 拥有独立的工作区。

### 为什么用 worktree 而不是复制目录

| 对比项 | 复制目录 | git worktree |
|--------|----------|--------------|
| git 历史 | 各自独立，无法共享 | 共享同一个 `.git`，commit 互通 |
| 分支锁定 | 无约束，可能改错分支 | 每个 worktree 锁定一个分支 |
| 磁盘占用 | 完整复制 | 只复制工作文件，共享 git 对象 |
| 清理 | 手动删除 | `git worktree remove` 一键清理 |
| 合并 | 需要手动同步 | 天然在同一个仓库，直接 merge |

### 工作区布局

```
D:\Hermes Agent CN Desktop\workspace\
├── artist-commission/              # 主工作区（一号使用，master 分支）
├── artist-commission-client/       # 二号工作区（client-frontend 分支）
├── artist-commission-backend/      # 三号工作区（backend-artist 分支）
└── artist-commission-bugfix/       # 五号工作区（bugfix 分支）
```

四号不需要独立工作区，直接在主工作区的 `docs/` 下修改需求文档。

### 创建命令

```powershell
# 在主工作区目录下执行
cd "D:\Hermes Agent CN Desktop\workspace\artist-commission"

# 二号工作区
git worktree add ../artist-commission-client -b feat/client-frontend-xxx master

# 三号工作区
git worktree add ../artist-commission-backend -b feat/backend-artist-xxx master

# 五号工作区
git worktree add ../artist-commission-bugfix -b fix/bug-xxx master
```

### 注意事项

- 每个 worktree 需要单独 `npm install`（`server/` 和 `web/` 各一次）
- 同一个分支不能同时被两个 worktree 检出
- 任务完成后，一号合并分支，然后 `git worktree remove ../artist-commission-xxx` 清理
- 各 worktree 中的 `node_modules/`、`data/`、`uploads/` 不共享，各自独立

### Hermes 启动方式

每个工作者 Agent 启动时，先 cd 到自己的工作区再启动 Hermes：

```powershell
# 二号
cd "D:\Hermes Agent CN Desktop\workspace\artist-commission-client"
hermes

# 三号
cd "D:\Hermes Agent CN Desktop\workspace\artist-commission-backend"
hermes

# 五号
cd "D:\Hermes Agent CN Desktop\workspace\artist-commission-bugfix"
hermes
```

各 Agent 的 SOUL.md 放在各自的 `$HERMES_HOME/SOUL.md`，定义其角色和约束。
如果使用 Hermes Profile 隔离（推荐），每个角色用独立 profile：`hermes -p agent-02` 等。

## 十一、CI 自动检查

每次 push 和 PR 会自动运行（`.github/workflows/ci.yml`）：

- `server/`：`npm ci` → `npx eslint .` → `npm test`（Vitest）
- `web/`：`npm ci` → `npx eslint .` → `npm run build`

CI 不通过则不允许合并。
