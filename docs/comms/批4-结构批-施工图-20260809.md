### 1.3 迁移 v52 设计（置零 → DROP，事务内安全）

```js
{
  version: 52,
  name: 'retire_installment_paid_columns',
  up(database) {
    backupDbBeforeMigration(52) // 先例：v49/v50 调用（init.js:1785/:1911）
    // 1) 清零冻结（防 DROP 前残留脏值；真实库当前 0 行非零，no-op）
    database.exec(`UPDATE order_payment_installments
      SET paid_cents = 0, status = 'pending', paid_at = NULL
      WHERE paid_cents <> 0 OR status <> 'pending' OR paid_at IS NOT NULL`)
    // 2) 列删除（幂等：列不存在即跳过）
    for (const col of ['paid_cents', 'status', 'paid_at', 'requested_at']) {
      const cols = database.prepare('PRAGMA table_info(order_payment_installments)').all().map(c => c.name)
      if (cols.includes(col)) database.exec(`ALTER TABLE order_payment_installments DROP COLUMN ${col}`)
    }
  }
}
```

**迁移安全评估**：
- DROP COLUMN 可行性已实测：better-sqlite3 11.10 自带 SQLite **3.49.2**（≥3.35），含内联 CHECK 的 TEXT 列 DROP 通过；本表无索引（`PRAGMA index_list` 空）、无视图/触发器、无其他表 FK 引用该两列 → 风险极低。
- 不需要 v43/v49/v50 的 `noTransaction + foreign_keys=OFF` 大阵仗：那是 DROP/RENAME **父表** 触发子表 CASCADE 的 v38 事故陷阱；本迁移只删列，无子表依赖，事务内执行即可（v38 教训记档：任何 DROP/RENAME 父表仍必须事务外）。
- 先例对照：v43 DROP addon 表（事务外+FK 关闭+foreign_key_check 双保险）、v49/v50 重建表（12 步官方流程）——本迁移形态简单得多，仅复用它们的 `backupDbBeforeMigration` 备份约定。
- 发布时序：代码停写（§1.2#1）+ 迁移 v52 同版本合入；启动 `initDatabase` 自动执行；容器重建即生效，无灰度窗口（迁移跑在服务接受流量前）。
- 兜底：若对 DROP 仍不放心，降级方案 B = 迁移只做「置零冻结」（删掉第 2 步），列保留但永不再写；代价是双源列继续占位、REQ-025 §8.2 验收第 4 条「写路径消失」不彻底。推荐 A（DROP），理由：脏数据 0 行 + 无 schema 引用 + SQLite 版本满足 + 备份机制成熟（v43/v49/v50 同模式）。

### 2.2 活跃订单引用收款节点快照的全部路径

订单的收款节点是**创建时快照**（只落 `label/basis_points/amount_cents`，无 stage_id FK），而锁定推导读**实时模板**——这是 B10 错乱根因：

1. **快照写入**：`createOrder` → order.service.ts:246-261（下单时按 live `artist_workflow_stages` 收款节点 `allocateInitial` 落快照）；`promoteOrder`（:1083-1102）→ `generateInstallmentsForOrder`（:1047-1081，幂等，按 live 模板生成）。
2. **锁定位推导**：`getCompletedPaymentStageIndex`（order.service.ts:771-789）用 **live stages** 的 `takes_payment/sort_order` 推 `completedStageIndex` → `refreshInstallmentLocks`（:830-842，addPayment :1201 与 advanceStage order-workflow.service.ts:46 调用）→ `computeLockedState` 多锁/少锁；`applyDeltaToInstallments`（:797-828，:809）用同一推导 → 后续加减价**摊错节点**（改到已收/已锁节点）。
3. **状态映射**：`advanceStage/rollbackStage`（order-workflow.service.ts:37-80/:102-143）用 live stages 的 `mapStageToStatus`（下标语义：`idx===1 && takes_payment → confirmed`、最后 → done）→ 排序变更会让同一订单下一次推进映射出不同状态。
4. **展示分叉**：画师端 `getWorkflow`（order.routes.ts:189）/公开报价 `getPaymentPlan`（pricing.routes.ts:36）读 live；客户进度页/画师节点收款读快照（`getOrderInstallments`）。

结论：**收款开关切换与排序变更会直接破坏活跃订单的锁定/状态推导；比例（savePayment）只影响未来订单（快照 `basis_points` 与分摊均取快照，见 `readInstallmentState` :751-769 与 §1 论证），不破坏现有订单，但按派工口径统一纳入守卫。**

### 2.3 守卫行为设计

- **粒度：画师级**。订单快照无 stage_id 关联，无法定位「具体节点」；收款节点数/顺序变更影响该画师全部活跃订单的锁推导 → 以「该画师存在非终态订单且已生成分期快照」为拒绝条件（与 `resetArtistStages` 的 artist 级先例一致，且更精确——只拦有分期快照的单，缓冲/0 价单不拦）。
- 新增私有 helper（放 `getStages` 附近）：

```ts
function countActivePaymentOrders(artistId: number): number {
  return (db.prepare(`
    SELECT COUNT(DISTINCT o.id) AS c
    FROM orders o
    JOIN order_payment_installments i ON i.order_id = o.id
    WHERE o.artist_id = ? AND o.status NOT IN ('delivered', 'cancelled')
  `).get(artistId) as { c: number }).c
}
```

- 挂点（均在事务内、首个写之前，避免 TOCTOU，对齐 P1-9 范式）：
  - `updateStage`：仅当 `fields.takesPayment !== undefined` 时 guard（改名/描述/话术/随机模板变更零风险，放行）。
  - `reorderStages`：事务内开头 guard（收款节点相对顺序变化 → `completedCount` 变化；且 `mapStageToStatus` 下标语义漂移）。
  - `savePayment`：事务内开头 guard（按拍板口径统一拒绝；备选「放行+提示仅影响新订单」见 §2.7）。
  - `addStage`：建议同守卫（插入节点会平移 `sort_order`，`mapStageToStatus` 的 `idx===1→confirmed` 语义对活跃订单漂移；`getCompletedPaymentStageIndex` 的计数不受影响但状态映射受影响）——若一号不想扩 scope，至少在本批记录为相邻风险。
- 返回：`throw new AppError(E.WORKFLOW_PAYMENT_IN_USE, 400, { count })`，前端 i18n 用 `{count}` 插值（对齐 `STAGES_RESET_BLOCKED` 既有链路，web/src/api/index.js:29 已支持 detail 插值）。
