## 二、接口契约（供二号 F1-2/3/4 前端对照）

```
POST /api/artist/orders/:id/publish-artwork   （画师登录）
请求体: { deliverableIds: number[](≥1), title: string(1-100), description?: string|null(≤500) }
成功 201: { artworks: [{ id, imagePath, title, description }, ...] }   // camelCase，一图一条
失败: 404 订单不存在/交付物不属于本订单 · 400 非delivered/非图片格式/title非法/ids空/路径非法
```

## 三、实际目录约定（派工要求核实）

## 四、与拆解/派工的偏差点（按"以现码为准"核实后记录）

1. **端点路径**：派工写 `POST /api/orders/:id/publish-artwork`，实际落在 `/api/artist/orders/:id/publish-artwork`。理由：现码 `/api/orders/*` 前缀全部是客户公开端点（track/my/lookup/delivery），画师订单动作统一在 `/api/artist/orders/:id/*`（requireOwnOrder 挂载处）。派工自己要求"参考现有订单端点归属校验写法，别另起一套"，故跟现行前缀。
2. **跨画师状态码**：派工要求 403，同时要求复用现有归属校验（别另起一套）——现行 `requireOwnOrder` 对"不存在或不属于你"统一 404（防订单 ID 枚举）。折中：**API 层 404**（保持 requireOwnOrder 现行惯例），**service 层二次防御返回 ORDER_NOT_OWNED 403**（派工契约保留，TC-PA-07 覆盖）。
3. **非图片交付物**：deliverables 允许 zip/psd/pdf 等格式，派工未覆盖。本实现限制发布仅接受图片扩展名（.jpg/.jpeg/.png/.webp/.gif，对齐 /api/upload/image 白名单），非图片 → 400 ILLEGAL_FILE_TYPE。前端勾选项应只展示图片类交付物。
4. **操作日志**：原计划写 order_activity_logs 留痕，核实发现 `action_type` 列有 DB CHECK 约束（6 值枚举），加 'publish_artwork' 需重建表迁移——本批禁动 init.js，故不写日志表；留痕由 artworks 行本身承担（created_at + image_path 可追溯）。**一号若要求日志留痕，需另开迁移批拍板。**
5. **去重行为**：deliverableIds 重复 → 去重后处理不报错（派工定案，TC-PA-03）。
6. **标题处理**：所建每条作品共用同一 title（派工第 4 条，"标题+序号"属下一批）。
7. **ajv removeAdditional**：额外字段静默剥离不拒绝（项目现行配置，TC-PA-16 按实际行为断言，对齐 TC-RT-12c）。
