## 任务 1（P1-1）：TOTP 重放防护

**现状**（已核实）：`totp.ts:129-144 verifyTotp` 纯函数校验（时间窗口内码有效即通过），无「已用码」记录；`auth.service.ts:146-149` 校验成功后仅清零失败计数。

**修复方案**（选实现优雅者）：
- **方案 A（推荐）**：新增表 `totp_used_codes`（artist_id + code_hash + used_at，唯一索引防并发），校验通过后**先插入再返回成功**（插入冲突 = 已用过 = 拒绝）。保留策略：7 天前记录清理（校验时顺带删 or 定时）。
  ```sql
  -- 迁移 v48
  CREATE TABLE IF NOT EXISTS totp_used_codes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    artist_id INTEGER NOT NULL,
    code_hash TEXT NOT NULL,
    used_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (artist_id, code_hash)
  );
  CREATE INDEX IF NOT EXISTS idx_totp_used_artist ON totp_used_codes(artist_id);
  ```
- **方案 B**：artists 表加 last_totp_counter 字段——只记录「最后已用 TOTP 的 time counter」，新码 counter <= 记录值则拒绝（TOTP 标准「consumed counter」方案）。更轻（无新表），但需注意 time-step 漂移（用户设备时钟慢时 counter 会回退——**可能误锁**）。
- **⚠️ 推荐方案 A**（哈希表）：不依赖 counter 单调性，只有「同码用过」才拒绝，兼容时钟漂移。code_hash = `sha256(artistId + code + timeStep)` 或 `sha256(code + timeStep)`（按 30s step 计算——同一 timeStep 同码只准一次）。
- 清理：校验时顺带 `DELETE FROM totp_used_codes WHERE used_at < datetime('now','-7 days')`（低频操作，可接受）。

**验收**：同一验证码在同一 90 秒窗口内第二次使用 → 拒绝；新窗口新码 → 通过；回归测试全绿。

## 任务 2（P1-3）：金额聚合 ROUND

**现状**（已核实）：`price.ts:10-14 PRICE_FALLBACK_SQL` 三级回退（final→total→snapshot×100）SQL 侧无 ROUND；`price.ts:23` JS 侧 resolvePriceCents 有 Math.round。存量订单走 snapshot 路径时 SQL 聚合（SUM）浮点误差。

**修复方案**：
- `PRICE_FALLBACK_SQL` 外层包 `CAST(ROUND(<case>) AS INTEGER)`（或确认调用方 JS 侧已 round——先读全库使用点，确定哪些路径缺 ROUND）
- ⚠️ 保守：先 grep `PRICE_FALLBACK_SQL` 所有使用点，逐个确认「SQL 聚合场景」（SUM 里用）vs「单行取值场景」（JS 侧已有 round）——**只修缺 ROUND 的聚合路径**，不全局替换（避免无关 diff）
- 若确认所有使用点 JS 侧都有 round：报告说明「已安全」，无需改（如实，不硬改）

**验收**：金额聚合路径浮点误差消除（测试用 0.1 类小数验证）；无行为变化。
