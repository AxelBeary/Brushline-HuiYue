## 现状问题（一句话）

详情页同时显示两套状态系统——上面固定五步条说"制作中"，下面工作流卡片说"线稿 4/7"，信息矛盾，按钮分散在两处，画师不知道用哪个。

## 已核实的后端规则（三个方案共用的事实基础）

1. **有工作流的订单，固定状态按钮已被后端禁用**：`updateStatus` 接口对有 `currentStageId` 的订单直接报错（cancelled 除外）。也就是说现在详情页上"确认/开始制作/完成"那些按钮，在工作流订单上点了就报错——**不是体验问题，是功能冲突**。
2. **stage 推进自动联动 status**：推到最后节点 → done，打回 → revision，不需要画师手动改状态。
3. **"最后活动时间"数据已有**：订单接口返回 `updated_at`，前端直接可用，不需要后端改动。
4. **⚠️ 后端缺口（需三号配合）**：老订单"启用流程跟踪"没有现成接口。现有 `advanceStage` 对无跟踪订单会把 status 重置为 pending（状态倒退，不可接受）。**需要三号加一个"开启跟踪"接口**（设 currentStageId = 第一节点，status 保持不变）。三个方案都含"启用跟踪"按钮（C53），实施时等三号接口就绪即可，不阻塞前端方案选择。

## 三个方案的公共部分（C52/C53 已拍板，不讨论）

- 有工作流 → 固定 el-steps **完全隐藏**，工作流进度条为唯一状态展示
- 无工作流 → 兜底卡片：状态标签 + **最后活动时间** + 备注数 + 参考图数 + 轻量提示"启用流程跟踪"（C53）+ 启用按钮
- 取消订单 → 滑块确认（复用 QueueBoard 的 SlideCancel，R30e 已有实现）
- 终态（已交付/已取消）→ 只读状态横幅，无操作按钮
- 客户 track 页不受影响

## 方案 A：单卡片模式切换（最保守，改动最小）

一个"状态"卡片，内部按有无工作流切换内容。操作按钮跟着内容走。

```
┌─ 状态 ─────────────────────────────────────────────┐
│                                                     │
│  【有工作流时】                                      │
│  ○定稿──●排期──○草稿──○线稿──○上色──○完稿──○交付     │
│  当前：排期确认（2/7）  最后活动：今天 14:30          │
│  [推进 → 草稿]  [↩ 打回]              [取消订单]     │
│                                                     │
│  【无工作流时】                                      │
│  ● 制作中   最后活动：今天 14:30                     │
│  备注 3 条 · 参考图 5 张                             │
│  💡 启用流程跟踪，获得更细粒度的进度管理 [启用]       │
│  [标记完成]  [上传交付]               [取消订单]     │
│                                                     │
│  【已交付/已取消】                                   │
│  ✅ 已交付 · 完成于 2026-07-28                       │
│                                                     │
└─────────────────────────────────────────────────────┘
```

- 优点：改动最小，一个卡片搞定，页面结构不变
- 缺点：按钮位置随模式跳动（工作流模式按钮在时间线下方，兜底模式按钮在提示下方）；"看状态"和"做操作"混在一个卡片里

## 方案 B：状态卡 + 固定操作条（推荐）

状态卡片**只负责看**，操作收敛到一条**永远在同一位置**的操作条——不管状态区内容怎么变，按钮永远在状态卡下方、图库卡上方。

```
┌─ 状态 ─────────────────────────────────────────────┐
│  【有工作流时】                                      │
│  ○定稿──●排期──○草稿──○线稿──○上色──○完稿──○交付     │
│  当前：排期确认（2/7）  最后活动：今天 14:30          │
│                                                     │
│  【无工作流时】                                      │
│  ● 制作中   最后活动：今天 14:30                     │
│  备注 3 条 · 参考图 5 张                             │
│  💡 启用流程跟踪，获得更细粒度的进度管理 [启用]       │
└─────────────────────────────────────────────────────┘
┌─ 操作 ─────────────────────────────────────────────┐
│  [推进 → 草稿]  [↩ 打回]            [取消订单]       │  ← 永远在这个位置
└─────────────────────────────────────────────────────┘
┌─ 订单图库 ─────────────────────────────────────────┐
│  ...                                                │
```

- 操作条内容随状态自动切换：
  - 有工作流：`[推进 → 下一节点]` `[↩ 打回]` + 右侧 `[取消订单]`
  - 无工作流：按固定状态显示 `[确认]`/`[开始制作]`/`[标记完成]`/`[上传交付]` + 右侧 `[取消订单]`
  - 终态：操作条整条隐藏
- 优点：**操作位置固定 = 肌肉记忆**，画师永远知道按钮在哪；状态和操作职责分离，卡片语义清晰；改动量中等
- 缺点：多一个卡片，页面稍长（约 60px）

## 方案 C：指挥中心横幅（最激进，视觉最强）

状态卡顶部做一个"当前焦点"横幅：当前节点名放大成视觉主角，右侧直接放主操作。一眼看到"我在哪 + 下一步干什么"。

```
┌─ 状态 ─────────────────────────────────────────────┐
│  ╔══════════════════════════════════════════════╗   │
│  ║  当前阶段                          2 / 7     ║   │
│  ║  排期确认                     [推进 → 草稿]  ║   │
│  ║  最后活动：今天 14:30          [↩ 打回]      ║   │
│  ╚══════════════════════════════════════════════╝   │
│  ○定稿──●排期──○草稿──○线稿──○上色──○完稿──○交付     │
│                                     [取消订单]       │
│                                                     │
│  【无工作流时】横幅变为：                             │
│  ╔══════════════════════════════════════════════╗   │
│  ║  制作中                        [标记完成]    ║   │
│  ║  最后活动：今天 14:30 · 备注3 · 图5          ║   │
│  ║  💡 启用流程跟踪 [启用]        [取消订单]    ║   │
│  ╚══════════════════════════════════════════════╝   │
└─────────────────────────────────────────────────────┘
```

- 优点："我在哪、下一步干什么"的信息传达最强；主操作和当前阶段紧挨，视线不用移动
- 缺点：横幅风格偏强，和详情页其他 el-card 的朴素风格有落差；改动量最大；节点少（2~3 个）的画师会觉得横幅"用力过猛"

---

## 二号推荐：方案 B

理由：
1. **"操作入口收敛到一个区域"的最佳答案是"固定位置"**——B 的操作条不随内容跳动，A 会跳，C 虽然不跳但和状态展示混在一起
2. 状态卡纯展示、操作条纯动作，职责单一，后续维护（加按钮、改逻辑）只动操作条
3. 改动量适中，且未来想升级到 C 的横幅风格只需改状态卡内部，操作条可复用
4. B 的"多一个卡片"代价很小（60px），换来的是操作位置永远可预期
