## 二、后端改动（精确）

### 1. `server/src/features/tracking/tracking.service.ts`：`getArtistTrackingSummary` 增加 byDay

```ts
export function getArtistTrackingSummary(artistId: number, days: number): ArtistTrackingSummary & { byDay: Array<{ day: string; count: number }> } {
  const since = `datetime('now', '-${days} days')`
  const total = ...
  const byName = ...
  const byDay = db.prepare(`
    SELECT date(created_at, 'localtime') AS day, COUNT(*) AS count FROM events
    WHERE artist_id = ? AND created_at >= ${since}
    GROUP BY day ORDER BY day ASC
  `).all(artistId) as Array<{ day: string; count: number }>
  return { total, byName, byDay }

```
- 接口类型 `ArtistTrackingSummary` 相应加 `byDay`（或新建 `ArtistTrackingSummaryFull`）。

### 2. **性能关键：events 表加 artist_id 索引（迁移 v45）**

现状：events 只有 `idx_events_name_ts(name, ts)`，**无 artist_id 索引**——画师查询 `WHERE artist_id = ?` 会全表扫描，数据量上来后慢。加复合索引：

在 `server/src/db/init.js` 追加迁移 v45：
```js
{
  version: 45,
  name: 'tracking_events_artist_index',
  migrate(db) {
    db.exec('CREATE INDEX IF NOT EXISTS idx_events_artist_ts ON events(artist_id, ts)')
  }
}
```
- ⚠️ **CREATE INDEX 安全**：非 DROP/RENAME 父表，事务内可执行（v38 事故教训仅针对 DROP/RENAME）。
- ⚠️ 迁移追加位置：MIGRATIONS 数组末尾（紧跟 v44），确认数组内 version 递增、无重复。
- 已有库升级：schema_migrations 会记录 v45，幂等守卫（IF NOT EXISTS）保证重跑安全。
- **测试**：`server/tests/migration-v44.test.js` 有先例——新增或扩展迁移测试（跑 v45 后查 `sqlite_master` 确认索引存在）。

### 3. 防刷：画师 summary 接口加限流（并修复四号巡检 R1）

**背景**：四号代码健康巡检（`docs/comms/04-to-01-代码健康巡检-交付-20260807.md`）发现 **R1 真实隐患（中）**：`POST /api/anon-token` 无鉴权无限流（每次调用 INSERT 一行），且 `/api/events` 限流 key = `body.token || request.ip`（tracking.routes.ts:76）——攻击者可循环「签发新 token → 用新 token 发 50 条事件」完全绕过 IP 限流，两张表可无限刷大。**本批必须一并修复**（用户明确要求防刷）。

`server/src/features/tracking/tracking.routes.ts`：

**(a) 画师 summary 加限流**（同画师每分钟最多 30 次）：
```ts
fastify.get('/api/artist/tracking/summary', { preHandler: requireAuth }, async (request, reply) => {
  // 防刷：同画师每分钟最多 30 次（画师正常看页不会超过）
  if (!rateLimit(`artist-tracking:${request.artist.id}`, 30, 60_000)) {
    return reply.code(429).send({ code: 'RATE_LIMITED', error: '操作过于频繁，请稍后再试' })
  }
  ...
})
```
- ⚠️ handler 加 `reply` 参数；rateLimit import 已有（POST /api/events 用了）则复用。

**(b) R1 修复①：anon-token 签发加 per-IP 限流**（10 次/分钟）：
```ts
fastify.post('/api/anon-token', async (request, reply) => {
  // R1 修复：防刷——同 IP 每分钟最多 10 次（正常前端首次上报 1 次/会话）
  if (!rateLimit(`anon-token:${request.ip}`, 10, 60_000)) {
    return reply.code(429).send({ code: 'RATE_LIMITED', error: '操作过于频繁，请稍后再试' })
  }
  const token = trackingService.issueAnonToken()
  return { token }
})
```
- ⚠️ anon-token 无鉴权，`request.ip` 为唯一维度；前端每次上报前自动调一次（track.js），10 次/分钟足够宽松。

**(c) R1 修复②：events 限流 key 改双因子** `body.token + request.ip`：
```ts
const limitKey = body.token ? `${body.token}:${request.ip}` : request.ip
```
- 这样攻击者拿新 token 换 key 也没用（IP 维度仍卡住）；正常用户 token 维度不变。
- ⚠️ 注意：改动后跑 tracking.test.js 的 RATE_LIMITED 用例——原用例用同 token 连发 100 条验证限流，双因子 key 下行为不变（token 相同则 key 相同），测试应仍过；若有断言依赖旧 key 形式，同步更新。

**(d) 管理员 summary 加限流**（同管理员 30/60s，防管理员接口被刷）。

### 3.5 补充测试（R1 防刷用例）
- anon-token 同 IP 连发 11 次 → 第 11 次 429
- events 双因子：同 IP 换新 token 连发 → 仍触发 429（验证绕过已堵）

### 4. 契约（给前端）
- `GET /api/artist/tracking/summary?days=14` → `{ enabled, total, byName[], byDay[] }`
  - byDay.day = `YYYY-MM-DD`（本地时区），按日升序
  - byName 已按 count DESC
- `GET /api/admin/tracking/summary?days=30` → 不变（byDay 已有）
- 429 响应 `{ code: 'RATE_LIMITED', error: '操作过于频繁，请稍后再试' }`
