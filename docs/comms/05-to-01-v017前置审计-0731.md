### B2. v17 迁移陷阱预警

v17 将新增 `platform_urls` + `inspiration_tags`。基于 v1–v16 的模式和 SQLite 特性，需注意：

#### 陷阱 1：schema 与迁移必须同步更新
`init.js` 顶部的 `schema` 字符串是**新库建表用的完整结构**。v17 迁移加列的同时，必须把新列加入 schema 字符串，否则：
- 新部署的库没有新列 → 迁移补上（正常）
- 但如果 schema 里没写，而代码里 SELECT * 读到了，不会报错（SQLite 动态列）
- **真正的风险**：如果未来某个迁移重建表（如 v13 那样），新列会丢失

**建议**：v17 迁移 PR 必须同时改 schema 字符串，审核时作为检查项。

#### 陷阱 2：JSON 字段在 SQLite 的存储
`platform_urls` 大概率是 JSON TEXT 列（同 custom_links 模式）。注意：
- SQLite 没有原生 JSON 类型，存的是 TEXT，JSON 校验必须在 service 层做
- `JSON.parse` 必须 try-catch（参考 getCustomLinks 的防御模式）
- 默认值用 `NULL`（不是 `'[]'`），配合 service 层回退逻辑
- 不要用 SQLite 的 `json_extract()` 做查询条件 — 性能差且版本依赖

#### 陷阱 3：inspiration_tags 的存储方案选择
两种方案：
- **方案 A：TEXT JSON 列**（同 custom_links）— 简单，适合标签数量少、不需要跨画师查询的场景
- **方案 B：独立表 + 关联表** — 适合标签需要全局管理、去重、统计的场景

**建议**：如果灵感标签是画师私有的（每个画师自己定义自己的标签），用方案 A（TEXT JSON）即可，与 custom_links 模式一致，迁移最简单。如果需要全局标签库（平台预定义 + 画师选择），用方案 B。

#### 陷阱 4：备份
v11、v12 有自动备份，v13–v16 没有。v17 改 artists 表，**建议恢复自动备份**（copyFileSync 模式），成本极低但关键时刻救命。

#### 陷阱 5：回滚方案
SQLite 不支持 `ALTER TABLE DROP COLUMN`（3.35.0+ 才支持，且限制多）。回滚策略：
- 新列是 NULL 默认 → 回滚 = 忽略新列，代码不读就行
- 如果 v17 有数据回填逻辑 → 回滚需要备份恢复
- **建议**：v17 迁移只做 ADD COLUMN + 建表，不做数据回填，降低回滚风险

#### 陷阱 6：cleanDb 和 seedArtist 同步
测试 setup.js 的 `cleanDb()` 和 `seedArtist()` 必须同步更新：
- 如果 inspiration_tags 是独立表，cleanDb 要加 DELETE
- 如果 artists 表加了新列，seedArtist 的 INSERT 不受影响（只写 5 列），但测试断言可能需要更新
