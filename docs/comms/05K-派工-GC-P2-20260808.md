## 任务 1（P0-2）：孤儿文件 GC 白名单机制

**现状**（已核实）：app.ts:37-118 GC collect 8 字段（references/deliverables/notes/artworks 等）依赖**人肉登记白名单**——R19 备注附图、v0.35 画风封面都出过「文件删了但 DB 还引用」事故（两次数据丢失）。

**改进方向**（选实现优雅且风险可控者，先出简短方案再改）：
- **方向 A（推荐）**：GC 改为「**黑名单/引用计数**」——collect 时查 DB 中该路径是否仍被任何表引用，被引用则跳过（从「白名单允许删」反转为「黑名单禁止删」——默认保守，漏登记只多留垃圾不丢数据）
- **方向 B**：GC 改为**只回收回收站内超期文件**（软删除已确认不用的），不主动 collect 业务目录——最保守但 GC 价值降低
- ⚠️ **安全底线**：任何改法必须保证「DB 有引用 → 文件绝不被删」。宁多留垃圾，不丢数据（两次事故教训）
- ⚠️ 先读 app.ts:37-118 完整 GC 逻辑 + 各 collect 字段的来源表，写清楚「黑名单判定需要查哪些表」
- ⚠️ 如果方向 A 涉及跨表查询较复杂：**降级为方向 B（只回收回收站）** + 报告说明，不强行复杂化

**验收**：GC 运行时，DB 仍引用的文件不被删除；测试覆盖「引用中不删 / 无引用可删 / 回收站超期删」。
