**根因**：`createArtist` 只检查了 `artist_code` 唯一性，未检查 `qq_number` 和 `subdomain`，INSERT 撞 UNIQUE 约束 → SQLite 原始错误 → 500。

### P1-7：docker 容器内 localhost 登录失败

**根因**：`index.js` 已绑 `0.0.0.0`（非 HOST 问题）。真正原因是 Node 22 的 `localhost` 优先解析为 `::1`（IPv6），但服务只听 IPv4 `0.0.0.0`，导致容器内 `fetch('http://localhost:3000')` 连接 `::1` 失败。

**修复**：`docker-compose.yml` healthcheck 的 `localhost` 改为 `127.0.0.1`，强制走 IPv4。

**改动文件**：
- `docker-compose.yml`：healthcheck test URL `localhost` → `127.0.0.1`

**注意**：容器重建后生效（`docker compose up -d --build`）。

## P1-5 方案：workflow 悬挂引用（待一号确认）

### 现象

画师删除 workflow stage 后，已有订单的 `current_stage_id` 仍指向已删除的 stage ID，导致订单详情页渲染异常（查 stage 返回 undefined）。

### 根因

`workflow.service.js` 的 `deleteStage`（第 190-218 行）直接 `DELETE FROM artist_workflow_stages WHERE id = ?`，不检查 `orders.current_stage_id` 是否引用该 stage。`orders.current_stage_id` 列无 FOREIGN KEY 约束（init.js 第 103 行），SQLite 不会自动阻止。

### 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A：阻止删除（推荐）** | 删除前查活跃订单引用，有则 400 拒绝 | 简单安全、不丢数据、业务语义正确 | 画师需先处理引用订单 |
| B：迁移引用 | 将引用订单迁移到相邻 stage | 画师操作不受阻 | 自动迁移可能语义错误（线稿→定稿？）、复杂度高 |
| C：级联置 NULL | 删除时将引用订单 current_stage_id 置 NULL | 简单 | 订单丢失工作流进度，画师需重新设置 |

### 推荐方案 A 细节

1. `deleteStage` 事务内，DELETE 前新增检查：
   ```sql
   SELECT COUNT(*) FROM orders
   WHERE current_stage_id = ? AND status NOT IN ('delivered', 'cancelled')
   ```
2. 有活跃订单 → 抛 `AppError(E.STAGE_IN_USE, 400, { count })`
3. 错误消息：`该节点下有 N 个进行中的订单，请先完成或转移后再删除`
4. 终态订单（delivered/cancelled）的悬挂引用不阻止删除，渲染层已有 null 保护（`order.current_stage_id ?? null`）

**改动范围**（预估）：
- `server/src/features/artist/workflow.service.js`：deleteStage 加 1 个 SELECT + 1 个 if
- `server/src/shared/errors.js`：新增 `STAGE_IN_USE` 错误码
- `server/tests/workflow.test.js`：新增 2 个测试（有活跃订单拒绝 / 无活跃订单允许）

**工时**：~30 分钟

2. 终态订单的悬挂引用是否需要额外清理（置 NULL）？还是渲染层 null 保护够用？
