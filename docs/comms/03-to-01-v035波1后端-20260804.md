## 给二号的 API 契约（波 2 消费）

### 1. GET /api/public/styles/:subdomain（扩展，数组结构不变）
sizes 每行新增字段：
- `image`: string|null — 独立上传图路径（images/ 公开目录，前端拼 `/uploads/` 前缀）
- `image_artwork_id`: number|null — 作品集引用 id
- `artwork_image_path`: string|null — 引用作品的实时图路径（**渲染优先级：image_artwork_id 有值用 artwork_image_path，否则 image，都无则画风封面兜底**——F3-3）
- `description`: string|null、`work_days`: number|null

**开关行为**：`multi_style_enabled=0`（迁移后所有画师默认）时**只返回默认画风**（排序最前的启用画风，动态顺延——最前被停用则取下一个）。开关=1 返回全部启用画风。二号无需自己过滤。

### 2. GET /api/public/gallery/:subdomain（新端点，F6 画廊）
```
{
  artworks: [{ id, image_path, title, description, like_count, is_cover, width, height,
               size_tags: [{ style_size_id, size_name, style_id, style_name }] }],
  filterSizes: [{ id, name, style_id, style_name, sort_order }]
}
```
- 开关门控同上：关闭画风的标注不出现在 size_tags 和 filterSizes（作品本体仍返回，只过滤标注）
- 删尺寸→标注 CASCADE 自动清理（F6 验收 8）
- 未标注作品 size_tags=[]（只在"全部"下可见——F6 验收 6 由前端实现）

### 3. PUT /api/artist/profile 新增 `multiStyleEnabled`: boolean
走现有 profile 更新链路，响应回带 `multi_style_enabled`。

### 4. 作品标注 API（波 3 后台 UI 消费，本波已就绪）
- `GET /api/artist/artworks` — 每作品附带 `size_tag_ids: number[]`
- `PUT /api/artist/artworks/:id` — body `{ title?, description? }`（均可选，maxLength 100/2000）
- `PUT /api/artist/artworks/:id/tags` — body `{ sizeIds: number[] }`（替换语义；跨画师尺寸→404 事务回滚）

## 设计决策（与派工预判的偏差说明）

1. **image/image_artwork_id 互斥语义**：后端「传一清一」——设作品集图时独立图清空，反之亦然。派工预判的"渲染优先级"保留，但存储上不会两值并存，前端判断更简单。
2. **F6 数据用独立端点**（不塞进 styles 数组）：artworks 体量大，避免下单流程每次多拉全量作品；且不动现有契约。
3. **后端未动 web/src/api/index.js**（共享文件权限）：新后台功能用现有 artistApi 方法（updateProfile/getProfile/getArtworks 等）即可覆盖。若波 3 需要 updateArtwork/setArtworkTags 封装，届时协调一号加两行或前端内联 fetch。
4. **旧 price_tiers 表不删**（派工已明确）：carol 迁移后 3 条旧档位保留，orders.tier_id 外键依赖。

## F5 回滚方案（高风险项）

**备份位置**：`data/commission.db.bak.v37`（迁移 up() 开头自动 copyFileSync，失败不阻塞但打 warn——与 v36 一致）。

**场景 A：迁移跑坏、服务未起**（最可能）
```
停服 → copy data/commission.db.bak.v37 → data/commission.db（覆盖）→ 起服
```
注意：恢复后 DB 无 v37 记录，若代码已含 v37 会重跑一次——迁移幂等，结果与首次一致，无副作用。若要彻底回到 v36：`git revert` 本分支两个 commit 再恢复备份。

**场景 B：迁移成功但业务要撤回 F5 数据**
carol 的新增数据可精确定位删除：`art_styles` 中 name='默认' 且无 cover_image 的行（v37 日志 `📦 迁移 F5: 画师 <id>` 记录了画师 id 和尺寸数）+ 其下 style_sizes；style_sizes 新字段 DROP 不回（SQLite 3.35+ 支持 DROP COLUMN，但无必要——字段为 null 不影响旧逻辑）。优先用场景 A 整体恢复，简单可靠。

**Docker 环境**：备份在容器内 `/app/data/commission.db.bak.v37`（bind mount 到宿主机 `data/`），宿主机可直接取。
