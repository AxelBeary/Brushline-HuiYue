## 需求基准

REQ-025 全文为准（R1~R12 + 边界案例 1~8）。以下是一号的实施裁决，有疑义以 REQ-025 原文 + 下列裁决为准，**不要自行扩大解释**：

### 1. 条目账本表（新迁移 v39）
- 新建 `order_price_entries` 表：order_id / type(base|manual_adjust|extra_item|discount_item|refund_item|extra_charge_after_close|extra_refund_after_close) / delta_cents / name / note / created_by / created_at
- **只追加不删不改**（schema 层不需要防 UPDATE，服务层不提供 UPDATE 路径即可）
- `orders.final_price_cents` 语义 = Σ 条目 delta（base 条目即初始报价）；创建订单时写 base 条目。**第一阶段只建表 + 写引擎，createOrder 的 base 条目写入也放到第二阶段**（避免动 createOrder）——第一阶段引擎从"给定条目列表"推导，测试用内存数据喂

### 2. 锁价与分摊（核心纯函数）
- `computeLockedState(installments, paidTotalCents, completedStageIndex)` → 每个节点 locked 状态（完成 OR 付清，先到先锁；R4）
- `allocateDelta(installments, lockedFlags, deltaCents)` → 未锁节点按原始 basis_points 归一化分摊，向下取整，尾差归最后一个未锁节点（R5/R6）；全锁时 delta 进额外应收/应退（R10）
- `deriveInstallmentProgress(installments, paidTotalCents)` → 顺序填充 + 超付抵扣的每节点 paid/remaining（R7/R8，尾款 remaining 可为负）
- `applyRefund(...)` → 镜像填充（R9）：冲未锁节点，冲到底尾款变负
- 每个函数纯函数无副作用，输入输出全部 cents 整数

### 3. 守恒断言（R11）
- `assertConservation(order, installments, entries, paidTotal)` 三条断言，失败抛 AppError（新错误码，如 PRICING_CONSERVATION）
- 引擎所有变动入口（第二阶段接）调用前自检；第一阶段只在测试里验证断言本身

### 4. 测试基准（硬指标）
REQ-025 第三节边界案例 1~8 **逐案例落成测试**，数值以文档纠正值为准（用户原稿笔误值已在文档中注明，不要用）。另补：
- 案例 9：0 节点订单（无收款节点的工作流）分摊 delta → 全进额外应收
- 案例 10：单节点 30%（比例和≠100%）场景，ratioTotal 按 30% 算
- 守恒断言的三条各造一个"故意破坏"用例，确认断言能抓住
- 测试文件独立（如 server/src/features/pricing/pricing-engine.test.ts），测试用内存构造数据，不依赖 DB 的话尽量纯函数测；需要 DB 的部分遵守测试隔离纪律（独立 DB_PATH）
