## 结论：当前零预留，全部等 v1.0

逐项判断：

### 1. API 层 — 不动

- 画师档案/委托列表/图片读取：现有 REST API 全覆盖，桌面端直接复用同一套 token 认证 + JSON API
- ETag/Last-Modified：@fastify/static 当前未配，但这是 v1.0 桌面端开发时的一行配置（`etag: true`），现在加没有消费者，纯增加响应头开销。**等 v1.0**

### 2. 数据模型 — 不动

- 本地记账（F2）是桌面端本地 SQLite，与平台订单模型无兼容需求。"本地委托→关联平台订单"是 v1.0+ 的功能设计，届时再定映射（现在定 = 猜，猜错 = 返工）
- profile 表字段对桌面端无缺失（桌面端额外需要的本地设置存桌面端自己的存储，不上平台）

### 3. 图片上传 — 不动

- 现有 multipart 上传 API 对任何 HTTP 客户端友好（不限浏览器），CORS 同源部署无限制。分片上传是 v1.0 性能优化，现在不需要

### 4. 认证 — 不动

- AUTH_DEV_MODE 是开发期产物。正式认证（JWT/refresh token/OAuth）等桌面端立项时一起设计——桌面端的认证需求（长期 token、离线容错）和 Web 不同，提前设计接口契约大概率猜偏。**过度预留 = 过度设计**

### 5. 其他 — 唯一值得保持的习惯

- API 版本化意识：未来破坏性变更走 `/api/v2/` 前缀而非原地改。这是零成本习惯，不需要现在写代码

## REQ-014 影响

无需更新。研判结论 = "平台侧当前无改动"，需求文档保持活文档状态即可。

## 一句话

桌面端是 v1.0+ 的事，现在平台侧做任何预留都是猜。唯一要做的是 v1.0 立项时把桌面端开发者拉进来审一遍 API——那是未来的事。
