## 逐条详情

### 🔴-1 [order.service.ts:699-707] adjustFinalPrice 金额回退链缺 price_snapshot，旧数据订单加/减附加项后丢原价

- 现象：`adjustFinalPrice` 读取当前价用的是 `order?.final_price_cents ?? order?.total_price_cents ?? 0`（order.service.ts:701），而全库统一的口径是 `resolvePriceCents`（utils/price.ts:16）：`final_price_cents ?? total_price_cents ?? price_snapshot×100`，三级回退。两者不一致。
- 触发条件：订单 `final_price_cents` 与 `total_price_cents` 均为 NULL、仅 `price_snapshot` 非空（v0.16 前旧数据/直插 DB 订单），画师对该单调用 addExtraItem / deleteExtraItem（order.service.ts:946、967 附近调用 adjustFinalPrice）。此时 currentFinal=0，`newFinal = 0 + deltaCents`，`final_price_cents` 被写成纯增量，原价（price_snapshot）丢失。
- 影响：金额错误（少收/多收）；且条目账本（ensureBaseEntry 已按 price_snapshot 补 base 条目）与 orders.final_price_cents 不一致——后续守恒断言/前端展示会互相矛盾。当前系统 createOrder 均写 final 或 total，故触发面限于历史存量订单，但金额错误属数据级错误。
- 建议修复（待一号拍板派修复批）：`const currentFinal = resolvePriceCents(order) ?? 0`（与 updateFinalPrice/ensureBaseEntry 口径统一，utils/price.ts 已导出该函数）。

### 🟡-1 [admin.routes.ts:76/727/746/757、artist.routes.ts:223/444、upload.routes.ts:176/211/245/279] catch-all 把非业务错误伪装成 400 并直出 err.message

- 现象：多个路由的 catch 块统一 `reply.code(e.statusCode || 400).send({ code: e.code || 'UNKNOWN', error: e.message })` 或 `reply.code(400).send({ error: (err as Error).message })`，未判断 `err instanceof AppError`。
- 触发条件：服务层抛非 AppError（SQLite 约束冲突、fs 错误、磁盘满等）——本应走全局 errorHandler 返回 500 结构化错误并记日志，却被 catch 截获转成 400 回显原始 message。
- 影响：①错误码不一致（服务器错误返回 4xx，前端/监控误判）；②内部细节泄露（表名/列名/绝对路径可能在 message 中出现）；③Sentry 收不到这类异常（被 catch 吞掉）。
- 建议：catch 内 `if (err instanceof AppError) return reply.code(...)...; throw err`，非业务错误向上抛走全局 500 handler。

### 🟡-2 [order.service.ts:373 + order-gallery.service.ts:44/72 + tryAutoPromote(order.service.ts:1115-1132)] 自动递补在交付事务内嵌套调用，递补失败回滚整个交付操作

- 现象：`updateOrderStatus`（order.service.ts:373）与 `deliverOrder`/`deliverOrderWithoutFile`（order-gallery.service.ts:44/72）在事务内调用 `tryAutoPromote`，而 `promoteOrder`（order.service.ts:1132 调用）内部又开事务并执行 `checkOrderConservation`（order.service.ts:1178）——守恒断言失败抛 AppError 时会向上一层传播，把外层「delivered 状态变更 + 交付文件行」整体回滚。
- 触发条件：缓冲区存在订单且其递补生成分期后守恒断言失败（异常比例配置/历史脏数据）。
- 影响：画师完成交付时因一单「顺带递补」失败导致交付动作本身失败（前端报错、文件行回滚），业务耦合错误。
- 建议：tryAutoPromote 内对 promoteOrder 的 AppError 做 catch（记日志 + 跳过该单继续/终止），递补失败不阻断主操作；或把自动递补移出事务外执行。

### 🟡-3 [artist.routes.ts:607-611] 公开 workflow 端点暴露画师话术模板（speech_template）

- 现象：`GET /api/artists/:subdomain/workflow`（公开）直接返回 `workflowService.getWorkflow(artist.id)`，StageCamel 含 `speechTemplate` 与 `randomTemplate`；订单 track 端点（order.routes.ts:191）同样返回完整 workflowStages。
- 影响：任意匿名访客可读到画师配置的客户沟通话术（可能含价格/催款措辞、随机模板开关）。若「客户端展示流程阶段」是产品需求，话术字段应视为附带暴露——需产品确认是否可接受，不接受则公开路径剥离 speech 字段。
- 建议：公开端点投影剔除 speechTemplate/randomTemplate（保留 name/description/isFinal），画师端/管理端走原 getWorkflow。

### 🟡-4 [pricing.routes.ts:216 + discount.service.ts:117] 折扣码过期时间无格式校验，new Date 解析时区语义不一致

- 现象：`expiresAt` schema 仅 `maxLength: 50`（pricing.routes.ts:216），任意字符串入库；验证时 `new Date(code.expires_at) < new Date()`（discount.service.ts:117）——无时区字符串（`YYYY-MM-DD HH:MM:SS`）按本地时间解析，带 `Z` 后缀按 UTC 解析，同一字段两种语义。
- 影响：画师设置的过期时间可能提前/延后数小时失效（与服务器时区相关），属边界行为不一致。
- 建议：schema 限定格式（如 ISO 8601 或 `YYYY-MM-DD HH:MM:SS`），服务层统一 toSqliteDate 规范化 + 与 SQLite 时间口径对齐（对照 updateDeadline 的 toSqliteDate 先例）。

### 🟡-5 [platform.service.ts:96] updatePlatform 对 match_domains JSON.parse 无兜底

- 现象：`match_domains: JSON.parse(existing.match_domains || '[]')` 直接解析存量数据，未 try/catch（同文件 rowToPlatform 有兜底，此处漏了）。
- 触发条件：存量 social_platforms.match_domains 损坏（手工改库/历史脏数据），管理员编辑该平台 → SyntaxError → 500 非结构化错误。
- 影响：单点崩溃（编辑一个坏平台即 500），且错误信息直出（若被 catch-all 捕获会泄露）。
- 建议：复用 rowToPlatform 的解析兜底（Array.isArray 过滤），失败按空表处理。

### 🟡-6 [order.service.ts:96-104] generateOrderNo 按 id DESC 取最大序号，物理删除后可能复用订单号

- 现象：`SELECT order_no ... ORDER BY id DESC LIMIT 1` 取「id 最大」而非「序号最大」的行；若某画师最大的订单行被物理删除（软删/取消不触发），新单序号回退复用。
- 影响：orders.order_no 有 UNIQUE 约束（init.js:112），复用 → 下单 500 回滚；当前系统无物理删单入口（取消为 status='cancelled' 保留行），风险低，但直插 DB / 未来加删单功能即踩坑。
- 建议：按 `ORDER BY order_no DESC` 取 max，或事务内 UNIQUE 冲突重试（生成新序号）。

### 🟢-1 [style-pricing.service.ts:137] radio 分支恒等赋值死代码

### 🟢-2 [order-queue.service.ts:150] getCompletedQueue 仍用 SELECT o.*（队列主体已显式列清单）

### 🟢-3 [guestbook.routes.ts:27] 留言 language 字段无 pattern 校验

- 现象：POST schema `language: { type: 'string', maxLength: 10, default: 'zh-CN' }` 无格式限制（GET 侧有正则兜底），任意 ≤10 字符入库。

### 🟢-4 [activity-log.service.ts:65] getOrderLogs 对 detail_json JSON.parse 无兜底

- 影响：detail_json 由服务层 JSON.stringify 写入，正常不会损坏；历史数据/手工改库损坏时该接口 500。
