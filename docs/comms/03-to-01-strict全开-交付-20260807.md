## 四、关键技术发现（与派工模板的偏差及原因）

**派工模板建议 handler 参数标注 `FastifyRequest`。实测发现该路线不可行：**

1. 三个 routes 文件的 120 处 TS7006 根因是 **fastify 参数未标注**——Fastify 路由回调参数本可由 `fastify.get(...)` 类型推断（`guestbook.routes.ts` 即先例：fastify 标注后 handler 零标注不报错）。
2. 但 Fastify 5 的 `FastifyRequest` 默认泛型下 `body/query/params` 均为 `unknown`（`request.d.ts` 中 `body: RequestType['body']` 延迟推断）。若强制标注 `FastifyRequest`，会新增约 100 处 TS18046/TS2339/TS2741（`request.body.code`、`request.params.id` 等全部失效），必须再为每个路由补 `as` 断言或泛型——工程量翻倍且易错。
3. 泛型接口不能简单 augmentation（`interface FastifyRequest { body: any }` 会因类型参数不一致报 TS2428）。

**故采用仓库既有先例**（`order.routes.ts` / `upload.routes.ts` 均已用 `request: any` 且通过 lint/test）：handler 参数显式 `: any`。显式 any 仍是"类型标注"（消除隐式 any TS7006），strict 门禁达成，零行为变化，与现有代码风格一致。已过 lint（eslint 无 no-explicit-any 规则）。

> 建议（不属本次范围）：后续可用 Fastify TypeProvider 或每路由泛型逐步替换 handler 的 any，单独立项。
