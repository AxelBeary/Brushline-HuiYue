## 任务理解

STATUS 遗留 P1-2：rate-limit.ts 用 `Map` + 60s 定时全扫（O(n)），超限时 `clear()` 全清。用户拍板 LRU 化——每次调用仅多一次 delete+set O(1)，消除定时全扫，超限精确淘汰。**行为完全不变铁律**：放行/限流判定、滑动窗口语义、MAX_BUCKETS 上限全部保持。全站限流核心（27 处接口依赖），保守 + 测试覆盖。

## 改动说明

### server/src/shared/middleware/rate-limit.ts（授权文件 1）

before：
- `rateLimit()`：get 桶 → shift 窗口外时间戳 → 判断 → push
- `_cleanup` 60s 定时器：全扫所有桶 shift 过期 + 空桶删除 + 超 MAX_BUCKETS 时 `buckets.clear()` 全清

after：
1. `rateLimit()` 内 LRU 刷新：取出的桶 `delete + set` 重插到 Map 末尾（最近访问）；新 key 插入后若超上限调用 `evictOldest(maxBuckets)` 精确淘汰
2. 保留窗口内 `shift` 过期时间戳逻辑（滑动日志语义，行为不变）
3. `setInterval(60s)` 定时器**保留**：仍做「空桶清理」防止永不活跃 key 堆积（保守保留现有清理逻辑）；仅将 `buckets.clear()` 超限分支替换为 `evictOldest(MAX_BUCKETS)` 精确淘汰
4. 新增 `evictOldest(maxBuckets)`：超上限时从 Map 头部（最久未访问）逐个删，直到达标
5. 新增可选参数 `maxBuckets`（默认 100_000）——测试可传小值（如 3）验证淘汰最旧，不改变现有调用方契约

### server/tests/rate-limit.test.js（授权文件 2）

新增 2 个测试（保留原有 5 个回归用例）：
- **TC-RL-06**：LRU 超限精确淘汰——maxBuckets=3 插入 10 个 key，最早访问的被淘汰（重新访问 → 放行），最近访问的保留（限流）
- **TC-RL-07**：访问刷新 LRU 顺序——访问 A、B、A（A 刷新为最近），插入 C 触发淘汰时淘汰 B（最久未访问）而非 A

## before/after 复杂度对比

| 维度 | before | after |
|------|--------|-------|
| 定时全扫 | 60s O(n)，n 最大 100k 桶 | 保留 60s 空桶清理（O(n) 仅处理不活跃桶），**不再承担超限保护职责** |
| 每次调用 | O(1) get/set | O(1) 多一次 delete+set |
| 超限处理 | `clear()` 全清（误杀所有限流状态） | `evictOldest()` 逐个淘汰最久未访问，精确到桶 |

## 风险与说明

1. **行为不变性**：rateLimit 放行/限流判定逻辑未动；`shift` 滑动窗口语义未动；MAX_BUCKETS 默认 100_000 未动。LRU 刷新仅在取桶后多一次 delete+set，对返回值零影响。
2. **定时器保留**：LRU 只替换「超限全清」；「key 不活跃但未超上限」的场景仍由 60s 定时清理空桶兜底（保守方案，符合施工图）。
3. **测试隔离**：TC-RL-06/07 使用独立 key 前缀（test-lru-* / test-lru-refresh-*），maxBuckets 仅影响本组测试的淘汰阈值，不污染其他用例。
4. **环境**：worktree 缺 node_modules，从主仓 robocopy 复制 + `npm install --no-save oxlint@^1.77.0` 补装（未改 package.json/lock）。
