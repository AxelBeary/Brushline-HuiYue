## 二、任务 1（P0-2）：GC 白名单 → 黑名单机制

### 方案选择：方向 A（黑名单/引用计数）

**现状问题**：app.ts 内联 `gcUploads` 显式 collect 8 字段（artworks.image_path / price_tiers.example_image / order_references.file_path / deliverables.file_path / artists.avatar / order_notes.image_path / art_styles.cover_image / style_sizes.image），依赖**人肉登记白名单**。R19 备注附图、v0.35 画风封面都因漏登记发生过「文件删了但 DB 还引用」事故（两次数据丢失）。

**改动（`server/src/app.ts`）**：
1. 保留显式 collect 8 字段（文档化清单 + 快速路径）
2. 新增**黑名单动态扫描**：遍历 `sqlite_master` 全部业务表（排除 `sqlite_%`），对每个 TEXT/CLOB 列取 DISTINCT 非空值，值含 `/` 或 `\`（路径形态）即加入 refs 保护集合。漏登记新表/新字段最多多留垃圾，**绝不丢数据**。
3. 新增**回收站 TTL**（验收「回收站超期删」）：`.recycle-bin/` 下超过 30 天的日期子目录整体物理删除（`rmSync`），防回收站无限膨胀；30 天保留期 = 软删除恢复窗口。

### 安全底线验证

- ✅ DB 有引用 → 文件绝不删（显式 collect + 黑名单动态扫描双保险）
- ✅ 黑名单判定查的表：不维护清单，动态遍历全部业务表（未来新增表/字段自动纳入）
- ✅ 路径长度 >512 的值跳过（长 JSON/正文不可能是相对路径，防内存膨胀）
- ✅ 画师表为空跳过回收保护保留（数据库异常兜底）
- ✅ 24h 冷却保留（新上传文件不立即回收）

## 四、任务 3（P2-1）：时区双口径统一

### 根因（实测发现，比派工描述更深）

dashboard.service.ts month/year 用 SQL `strftime('%d/%m', ..., 'localtime')` 分组、quarter 用 JS `new Date(completed_at.replace(' ','T'))` 解析——双口径并存。

**关键实测**：Windows + `TZ=Asia/Shanghai`（vitest 配置）下，better-sqlite3 的 `strftime('localtime')` 修饰符**失效**（CRT 不识别 IANA 时区名 → 退化为 UTC），与 Node 应用层 `date.ts`（本地时区换算）差一天。这是环境相关的不确定行为，正是"双口径"隐患根源。

### 改动（`server/src/features/artist/dashboard.service.ts`）

统一为**应用层换算**（与 date.ts 口径一致、环境无关）：
- 新增 `toLocalDate(utcStr)`：UTC 存储字符串补 `'Z'` 按 UTC 解析 → 取本地日期分量
- month / quarter / year 三个分支：SQL 只取 UTC 原始 `o.completed_at`，分组在 JS 用 `toLocalDate` 完成
- 彻底移除对 SQLite `strftime('localtime')` 的依赖（消除环境差异）

### 测试（dashboard.test.js 新增 3 用例）

| 用例 | 场景 | 结果 |
|------|------|------|
| TC-DASH-TZ-01 | 季度周分组——UTC 凌晨订单归入本地日期所在周（跨天边界） | ✅ |
| TC-DASH-TZ-02 | 季度周分组——第 14 天 23:59 不溢出到下周 | ✅ |
| TC-DASH-TZ-03 | 月维度——UTC 凌晨订单按本地日期落柱 | ✅ |
