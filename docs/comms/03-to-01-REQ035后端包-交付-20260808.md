## 四、口径说明（重要，三处与派工描述有出入）

1. **order_payments 表结构与派工描述不符**：派工说「id/order_id/amount_cents/type/paid_at 等」，实测表结构（init.js 行 ~236）为 `id/order_id/installment_id/amount_cents/note/created_at/created_by`——**无 type 列、无 paid_at 列**。「正数收款/负数退款」由 `amount_cents` 正负号区分（对照 order.service.ts addPayment 实现：负数=撤销/退款且强制带 note），日期列用 `created_at`。已按实测实现，未自创。

2. **getRevenue 口径 vs totalPaidCents 口径**：派工要求 totalPaidCents「order_payments 正数-负数 口径，对照 getRevenue」。实测 getRevenue（dashboard.service.ts）实际是**订单金额口径**（orders 表 PRICE_FALLBACK_SQL：final_price→total_price→price_snapshot×100），**不读 order_payments**。而 getClientSummary 的 totalPaidCents 语义是「该客户订单已收总额」，因此选用 `SUM(order_payments.amount_cents)`（收款正、退款负，正负相抵）——这是 order_payments 作为唯一收款流水表的自然口径，与派工「order_payments 正数-负数」的要求一致，但与 getRevenue 的订单定价口径不同（两表语义不同）。已在 tools.service.ts 注释 + 此处写明，请一号知悉。

3. **orders 无 deleted_at 列**：派工 SQL 写 `AND deleted_at IS NULL`，实测 orders 表无此列（软删除只在 artists 表）。故客户汇总/老客列表按 `artist_id + client_qq` 直接过滤，不加 deleted_at 条件。

4. **老客 days 口径**：`daysSinceLastOrder = 今天(本地) - lastOrderAt(本地)`，命中条件 `> days`（45 天前客户 days=30 命中 / days=60 不命中，测试覆盖）。订单 created_at 为 UTC，出库转 localtime 再算天数（与散单 income_date 本地口径对齐）。⚠️ 曾踩坑：初版用 toSqliteDate()（UTC）算「今天」导致差一天，已修为本地日期。

5. **CSV 日期口径**：order_payments.created_at（UTC）经 `strftime('%Y-%m-%d', created_at, 'localtime')` 转本地日期，与散单 income_date（本地日期）合并排序，保证同一报表口径。
