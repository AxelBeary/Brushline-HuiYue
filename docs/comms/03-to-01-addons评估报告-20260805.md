## Q2：addPayment 是否存在绕过引擎的旧写路径？

### Q2.1 全部写路径清单（grep `INSERT INTO order_payments` 全仓）

**全仓仅 1 处**：`server/src/features/order/order.service.ts:1177`，位于 `addPayment`（L1151-1206）事务内。

交叉验证（确认无变体写法）：
- `DELETE FROM order_payments` / `INSERT OR REPLACE|IGNORE INTO order_payments`：0 命中
- 测试目录直写 order_payments：0 命中（tests 全部通过 `orderService.addPayment()`，如 quota-pool.test.js、pricing-phase2.test.js）
- demo-data.ts：0 命中 order_payments（收款不走脚本直插）
- 冗余字段 `paid_total_cents` 的写点：仅 addPayment L1180 与迁移 v24 一次性存量换算（`init.js:1130-1136`，installments SUM → paid_total，属历史迁移非运行时路径）；无其他 UPDATE 点
- addPayment 唯一生产调用方：`order.routes.ts:992`（POST /api/artist/orders/:id/payments）

### Q2.2 合规性逐条核对（addPayment L1151-1206）

| 引擎联动 | 行号 | 状态 |
|----------|------|------|
| 校验（整数/非零/负数必须 note/撤销不超已收/installmentId 归属） | L1155-1173 | ✅ |
| INSERT 流水（installment_id 关联） | L1176-1178 | ✅ |
| UPDATE orders.paid_total_cents（同事务） | L1180-1181 | ✅ |
| UPDATE 节点 paid_cents + 付清标记 | L1184-1192 | ✅ |
| **refreshInstallmentLocks（R4 付清即锁，从 paid_total 顺序推导）** | L1196 | ✅ |
| logActivity 操作日志 | L1199 | ✅ |
| **checkOrderConservation（R11 守恒自检）** | L1202 | ✅ |

单一事务包裹（L1175），原子性成立。收款不改总价/节点价，故不触发 appendPriceEntry/allocateDelta——这是正确语义（支付不动账本），A2 待收由推导自然闭合。

### Q2.3 结论：**无绕过引擎的旧写路径。** order_payments 唯一写入口 = addPayment，引擎联动（installment 关联 / locked 推导 / 守恒自检 / 日志）全部齐备且同事务。历史路径（v24 迁移前分期直改 status='paid' 的旧模型）已无运行时写点，仅 v24 迁移做过一次性换算。
