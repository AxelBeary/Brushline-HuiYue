## 四、迁移安全评估与回滚方案

- DROP COLUMN 可行性：better-sqlite3 11.10 内置 SQLite 3.49.2（≥3.35）；目标表无索引、无视图/触发器、无其他表 FK 引用四列；只删列不删父表，事务内执行安全（对照 v49/v50 需事务外仅因 DROP/RENAME 父表触发 CASCADE，v38 教训不适用于本迁移）。
- 备份机制：`backupDbBeforeMigration(52)` 自动生成 `DB_PATH.bak.v52`（仅文件库），叠加既有每日备份双保险。
- 存量影响：真实库当前 23 行全部零值/pending，冻结为 no-op；用户已拍板“没有真数据随时可以删数据库内容”，不保留僵尸列。
- 迁移链自洽性：新库 base 无四列 → v5 `CREATE TABLE IF NOT EXISTS` 不复活 → v24 守卫跳过（空表）→ v33 幂等守卫加回 `paid_cents`（历史迁移，不可改）→ v52 最终删除 → 收尾四列不存在。旧库（四列形态）→ v24 照常换算 → v52 冻结+删列。
- 回滚方案：代码侧 revert 本批 4 个提交即可；数据库侧若已执行 v52，用 `.bak.v52` 或每日备份还原；SQLite 无便捷 ADD COLUMN 恢复完整 CHECK/默认语义，DROP 后不推荐手工补列。方案 B 无“新老库形态分叉”残留。
