## 根因（比派工单更深一层，一号请复核）

派工单根因：`Date.now()-86400000` 是本地昨天，created_at 存 UTC，凌晨跨日错位。
**实测发现更深的坑**：vitest 进程内 SQLite 的 `localtime` 修饰符在 Windows + TZ env 下**按 UTC 处理**（无 +8 偏移）：

```
（vitest 进程内实测 02:01，TZ=Asia/Shanghai）
node now        : 2026-08-08 02:01 GMT+0800  ← Node 本地今天
sqlite date('now','localtime') : 2026-08-07  ← SQLite localtime 实际无偏移
```

- SQL 分组 `date(created_at,'localtime')` → UTC 日：昨天 1 条(08-06) + 今天 2 条(08-07)
- 方案 A localDayStr（Node 本地日）：昨天=08-07 → `countByDay[08-07]=2`，**仍失败**
- 复跑实测：方案 A 一次通过、一次 expected 2 to be 1 —— 证实方案 A 在本环境不可靠

## 修复方案（实际采用：方案 B 变体）

断言日期**直接从 DB 取**，与 byDay 分组 SQL 完全同源：

```js
const dayRow = db.prepare("SELECT date('now', 'localtime', '-1 day') AS yesterday, date('now', 'localtime') AS today").get()
expect(countByDay[dayRow.yesterday]).toBe(1)
expect(countByDay[dayRow.today]).toBe(2)
```

- 不依赖 Node 本地时区，也不依赖 SQLite localtime 是否真的偏移——两边同用 SQLite localtime 口径，任何时区环境自洽
- 仅动测试断言，业务代码（tracking.service.ts byDay 按 localtime 分组）未动，生产口径不变
