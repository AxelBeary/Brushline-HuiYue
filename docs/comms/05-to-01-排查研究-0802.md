## 任务 1：#15 瀑布流跳动根因分析

### 根因链条

```
el-image lazy（滚到视口才加载）
  → 加载前：skeleton min-height: 200px（固定猜测值）
  → 加载后：width: 100% + height: auto → 真实高度（可能 120px~600px）
  → 高度差 ≠ 0 → CSS columns: 2 触发整列 reflow
  → 该列所有后续 item 位置跳动
  → 用户看到"图片加载完跳动挤掉上方的图"
```

**关键证据**：
- `TplGallery.vue` L106-108：`.tpl-gallery--masonry { columns: 2; column-gap: 20px; }`
- `TplGallery.vue` L125-131：skeleton `min-height: 200px`（固定值，非真实比例）
- `TplGallery.vue` L17：`el-image` 带 `lazy` 属性（IntersectionObserver 懒加载）
- `TplGallery.vue` L117-120：`.tpl-gallery-img { width: 100%; display: block; }`（无 height 约束，高度由图片自然比例决定）
- `artworks` 表（init.js L62-72）：**无 width/height 列**，前端无法预知图片比例
- 4 个模板（Classic/Folio/Gallery/Atelier）全部使用 `TplGallery` 组件，masonry 是默认 layout

### 为什么 v0.29 骨架占位没解决

skeleton 的 `min-height: 200px` 是固定值。真实图片高度 = 列宽 × (原图高/原图宽)。列宽约 340px（容器 700px / 2 列 - gap），一张 1080×1920 的图真实高度 ≈ 604px，一张 1920×1080 的图 ≈ 191px。200px 的猜测对竖图差 3 倍，对横图也差几十像素。**只要猜测值 ≠ 真实值，columns 布局必然 reflow。**

### 修复方案对比

| 方案 | 原理 | 工程量 | 效果 | 副作用 |
|------|------|--------|------|--------|
| **A. aspect-ratio 预留（推荐）** | 上传时 sharp 读 width/height 存 DB → 前端 `style="aspect-ratio: w/h"` 精确预留 | 中（迁移+上传+前端） | 零跳动 | 无 |
| B. CSS grid 替代 columns | 改 `grid-template-columns: repeat(2, 1fr)` + 固定 aspect-ratio | 小 | 无跳动 | 失去瀑布流错落感，变等高网格 |
| C. JS 绝对定位布局 | 计算每列累计高度，absolute 定位 | 大 | 零跳动 | 复杂度高，resize 需重算 |

### 推荐方案 A 详细步骤

1. **迁移 v30**：`ALTER TABLE artworks ADD COLUMN width INTEGER; ADD COLUMN height INTEGER;`
2. **上传时读取**：`createArtwork` 中用 sharp（已在技术路线）读 metadata，写入 width/height
3. **存量回填**：一次性脚本遍历 artworks，sharp 读取已有图片补 width/height
4. **前端预留**：TplGallery 的 el-image 外层 div 绑定 `:style="art.width && art.height ? { aspectRatio: art.width + '/' + art.height } : {}"`
5. **skeleton 保留**：作为无 width/height 时的兜底（存量未回填的图片）

方案 A 与现有 CSS columns 完全兼容——columns 布局下，item 高度由 aspect-ratio 决定，图片加载前后高度一致，零 reflow。且 sharp 读取尺寸是缩略图管线（F 类技术债）的前置步骤，一次投入两处受益。
