## 一句话描述
画师约稿管理平台：多画师共用一套系统，每人有独立子域名主页。客户零注册下单/查进度，画师通过后台或QQ Bot管理排期。沟通全走QQ，平台不经手钱。

## 技术栈
- 前端：Vue 3 + Element Plus + Pinia + vuedraggable
- 后端：Node.js + Fastify 5
- 数据库：SQLite (better-sqlite3, WAL 模式)
- 文件存储：本地磁盘 uploads/
- 反向代理：Caddy（泛解析 + 自动 HTTPS）
- 部署：Docker Compose
- 测试：Vitest（内存数据库，32 个用例）
- QQ Bot：NapCat/LLOneBot（Phase 2，OneBot 11 协议）

## 核心设计决策

### 1. Feature-based 目录（v0.2 重构）
- 每个业务域一个目录：`features/{auth,artist,order,upload,admin}/`
- 每个 feature 包含 `*.service.js`（业务逻辑）+ `*.routes.js`（HTTP 路由）
- 跨 feature 共用的放 `shared/`（validate、middleware）
- `app.js` 是应用工厂，`index.js` 只负责启动

### 2. 拖拽排序逻辑（重要！）
- 被拖动的订单获得 **目标位置的优先级**（不是交换）
- 同优先级的其他订单 **顺延**
- 实现在 `features/order/order.service.js` 的 `reorderQueueByDrag()`
- 前端用 vuedraggable，`@end` 事件触发后端重排

### 3. 双模式（自助 + 手动）
- 客户可以自助填表下单（source='self'）
- 画师可以手动录入（source='manual'）
- 两种进同一个队列，管理方式一致
- 画师可以把状态改为"排满/休息"来关闭自助下单

### 4. 认证方案
- 6位数字登录码，5分钟有效，3次错误锁定
- MVP阶段：登录码在 API 响应中返回（_dev_code 字段）
- Phase 2：通过 QQ Bot 私聊发送，删除 _dev_code
- 会话 Token：HMAC-SHA256 签名，base64url(artistId:timestamp:sig)，7天有效
- 无密码设计

### 5. 子域名方案
- 泛解析 DNS + Caddy 通配符
- 后端根据 Host header 或 URL 参数识别画师
- 开发环境用 ?artist=xxx 参数
- 生产环境从 hostname 提取子域名

### 6. 文件上传
- 上传路由在 `features/upload/upload.routes.js`
- 格式提示：非 JPG/PNG/WebP 弹提示但不阻止
- 限制：10MB/张，最多5张
- 截断时自动清理残留文件

### 7. 客户端零注册
- 客户不需要账号
- 凭订单号查进度
- 凭交付链接下载文件

## 已知注意事项
1. `server/src/app.js` 中 pino-pretty 是 dev 依赖，生产环境自动跳过（动态 import + try/catch）
2. `web/src/views/artist/OrderDetail.vue` 中 `window.open` 在 template 里直接调用，需要改为方法
3. 开发环境客户端页面用 `?artist=alice` 参数指定画师，生产环境靠子域名
4. Element Plus 的 ElMessage 在 ArtistHome.vue 中未 import（全局注册了所以能用，但最好显式导入）
5. Docker 多阶段构建：前端在 `frontend-build` 阶段编译，生产镜像只含 `--omit=dev` 后端依赖
6. 测试中 `auth.service.js` 的 SECRET 在模块加载时固定，vitest.config.js 的 env 必须在 import 前生效
7. `entrypoint.sh` 使用绝对路径（`/app/server/src/...`），不再依赖 CWD
8. `db/init.js` import 时无副作用，CLI 执行或 `tests/setup.js` 显式调用 `initDatabase(db)` 才建表
9. 所有路由层不含裸 SQL，业务查询统一在 `*.service.js` 中
10. `upload.routes.js` 的 `UPLOAD_DIR` 由 `app.js` 通过插件选项传入，保证与静态服务路径一致
