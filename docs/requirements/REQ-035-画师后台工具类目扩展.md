## 二、新想法①：单独计费工具

### 用户价值
画师接的活不全是「完整订单流程」：临时加改一张图、QQ 里客户直接转账的小单、非档位体系的散活——这些钱目前**没有入口记录**，收入导出（A1）也漏掉它们。单独计费工具 = 给散单一个轻量记账入口，收入账本完整。

### 画师使用场景
- 客户微信/QQ 转 50 元让加个改图，画师随手记一笔：金额 + 客户 + 备注 + 日期
- 线下展会/朋友介绍的活，不走平台订单，但报税/复盘时钱要算进去

### 输入 / 输出
- 输入：金额（必填）+ 客户昵称/QQ（建议填）+ 备注 + 日期（默认今天）
- 输出：散单收入列表；**A1 导出 CSV 时合并散单流水**（同列：日期/客户/金额/类型=散单）

### MVP 可拆
- MVP：记账 CRUD（增/列表/删）+ 并入 A1 导出
- P2：按客户聚合散单统计、散单改单、标签联动（②）

### 工作量粗估
后端 1 表（standalone_incomes）+ 2 端点 + 前端 1 页 + A1 导出合并 ≈ **1~1.5 天**

### 拍板结论（2026-08-07 用户确认，原话「以上所有全部交给一号」）
1. ✅ **含义 = 散单收入记账**（不走订单流程、不入队列，只记钱）。~~订单内单项目计费~~（REQ-025 已覆盖，不做）
2. ✅ 散单**计入**画师收入口径（A1 导出合并；统计页口径待一号排期时定义，若并入需说明口径变化）

## 三、新想法②：客户标记（标签 / 备注）

### 用户价值
接单时 3 秒了解客户：是不是老客、上次合作如何、有没有坑（砍价/催稿/难沟通）、特殊偏好（厚涂/古风/不吃辣——不，是画风偏好）。目前只有 QQ 历史订单面板（按 QQ 查逐单），**没有客户级记忆**。

### 画师使用场景
- 录单页输入 QQ → 历史面板显示该客户标签（「老客户」「砍价」「急单」「好说话」）+ 备注（「喜欢厚涂，周末才回消息」）
- 已有备案支撑：FB-13 + REQ-031 §三 C1「回头客统计与客户标签」——手动录单 QQ 历史面板缺**汇总行**（共 N 单/累计金额/最近一单）与**自定义标签**，归本批次统一设计

### 输入 / 输出
- 输入：标签（多选，自定义可增删）+ 备注（一段文字），挂客户维度（按 client_qq）
- 输出：录单页历史面板展示（标签胶囊 + 备注行 + 汇总行）

### MVP 可拆
- MVP：客户标签 CRUD + 录单页展示 + 历史面板汇总行（共 N 单/累计金额/最近一单——**与⑥老客召回共享**）
- P2：标签筛选/统计、标签自动建议（老客=历史≥2 单）

### 工作量粗估
后端 1 表（client_profiles：artist_id + client_qq 唯一）+ 端点 + ManualOrderLeft 面板扩展 ≈ **1.5~2 天**

### 拍板结论（2026-08-07 用户确认）
1. ✅ 标签**画师私有**（客户不可见）
2. ✅ 客户维度键 = **client_qq**（现状必填字段）；其他平台客户（FB-39）暂不处理

## 四、新想法③：「今天吃什么」小工具（2026-08-07 用户拍板：四大类扩展版）

### 用户价值
纯娱乐/陪伴型小工具，工具类目「当卖点」的趣味担当。画师长时间赶稿，纠结午饭吃什么——点一下随机推荐，减少决策疲劳。**用户 2026-08-07 拍板扩展：吃的要够多，分健康 / 糖尿病 / 痛风 / 外卖四大类**。

### 画师使用场景
- 打开工具页 → 选模式（**四大类**）→ 点「随机推荐」→ 出结果（菜品名 + 分类 + 一句话点评）
- 不满意可「换一个」；可标记「今天吃这个」

### 四类内容定义（2026-08-07 用户拍板）
| 模式 | 内容方向 | 菜谱要求 |
|------|---------|---------|
| 健康版 | 低卡/清淡/营养均衡家常菜 | 每类 ≥30 条，全内置 |
| 糖尿病版 | 低 GI/控糖友好的主食与菜 | 每类 ≥30 条，标注「低GI」等提示 |
| 痛风版 | 低嘌呤友好（避开海鲜/内脏/浓汤） | 每类 ≥30 条，标注「低嘌呤」提示 |
| 外卖版 | 直接可点的外卖品类/店型推荐 | 每类 ≥30 条，含常见外卖平台可搜品类 |

> 菜谱量：**四大类合计 ≥120 条**（每类 30 条起步，鼓励更多），纯前端常量文件（如 `web/src/utils/food-menu.js`），不引外部 API。健康/糖尿病/痛风版可对同一菜品打多标签（如「清蒸鲈鱼」=健康+糖尿病+痛风都可用），避免硬凑 120 条注水。

### 输入 / 输出
- 输入：模式选择（健康/糖尿病/痛风/外卖）+ 点击随机
- 输出：随机菜品卡片（名称/类别/标签/一句话点评）+ 「换一个」按钮

### MVP 可拆
- MVP：四个菜谱库（各 30 条）+ 随机 + 模式切换 + 换一个
- P2：自定义菜谱（localStorage）、忌口排除勾选（原清单就有「忌口勾选」，P2 补）、「今天吃过」历史、分享到社媒（配合 B1 文案）

### 工作量粗估
- MVP：纯前端 1 页 + 1 数据文件 + locales ≈ **0.5~1 天**（无后端、无 DB、无迁移）
- P2（忌口/历史/分享）：+0.5~1 天

### 拍板结论（2026-08-07 用户确认）
1. ✅ 菜谱内容由四号编排（**内置固定，每类 30~50 条，质量优先不注水**，跨类打标签共用池子），画师自定义 P2
2. ✅ 糖尿病/痛风版加**免责提示**：「本推荐仅供参考，具体饮食请遵医嘱。」（一行小字 + i18n 两个键）
3. ✅ 暂定**四类**（健康/糖尿病/痛风/外卖），第五类（素食/省钱）后置

## 五、新想法④：跨平台消息解析创建订单（重头）

### 用户价值
画师接单主战场是 QQ/微信，客户发一大段约稿消息（QQ 号、需求、预算、截稿日、参考图），画师要**手动把这些信息搬运到录单表单**——重复劳动 + 容易漏。跨平台接单整合 = 复制聊天消息 → 自动解析 → 预填录单表单 → 画师确认提交。

### 画师使用场景
- QQ 收到客户消息：「QQ123456 想约一张半身像，预算 300，下周要，参考图 QQ 里发你了」
- 画师全选复制 → 打开「手动录单」→ 粘贴 → 系统解析出 client_qq=123456 / description=... / 预算线索 / 截稿线索 → **预填表单** → 画师检查补全 → 提交

### 输入 / 输出
- 输入：一段自由文本（QQ/微信/其他平台聊天记录复制粘贴）
- 输出：解析出的结构化字段（client_qq / client_name / description / 预算线索 / 日期线索 / 档位线索），预填 ManualOrder 表单，**可编辑**

### 关键设计约束（防屎山）
1. **解析是预填不是自动建单**——解析结果必须人工确认后才创建订单
2. **解析不出就不猜**——QQ 号识别不到就留空让画师填，绝不用假值凑
3. 规则解析（正则/关键词），**不引 AI 模型、不引外部 API**（零预算，且自由文本解析不需要 LLM）
4. 优先识别：QQ 号（5-15 位纯数字，消息中第一个独立数字串）、客户昵称（「我是xx」/「昵称：xx」）、需求描述（全文作为 description 预填）、金额线索（「预算 x 元」/「x 元」）、截稿线索（「x号前」/「x月x日」）
5. 档位/画风/尺寸**不自动匹配**（避免猜错绑错，画师专业判断），但可提示「检测到关键词：半身像」供画师点选

### MVP 可拆
- MVP-1：粘贴框 + 解析 QQ 号 + 全文预填 description + 识别金额/日期线索 → 预填后画师确认提交
- MVP-2：昵称识别 + 关键词→档位提示
- MVP-3：其他平台（微信/微博私信）模板微调

### 工作量粗估
- MVP-1：前端解析器 + ManualOrder 粘贴入口 ≈ **1.5~2 天**（纯前端，后端零改动——orders 字段全在）
- 完整（含 MVP-2/3）：+1 天

### 拍板结论（2026-08-07 用户确认）
1. ✅ 入口 = **ManualOrder 页顶部「粘贴消息解析」按钮**（录单流程内嵌，不跳页）
2. ✅ MVP-1 只做「QQ 号 + 全文描述 + 金额/日期线索提示」，档位/画风**不自动填**（避免猜错）
3. ✅ 参考图**无法解析**（跨平台拿不到原图），画师手动上传，接受边界
4. 是否需要「解析历史」（保留最近解析记录，便于多次粘贴同客户消息）？建议 P2

## 六、新想法⑤：图片水印工具（2026-08-07 用户拍板：全面版）

### 用户价值
画师把完稿发微博/B站/小红书前，想打上自己的名字/主页链接/LOGO 防盗图。目前要手动用第三方工具（美图/PS），水印文案每次手打。工具 = 内置水印工具，**传图/选图 → 选水印（画师名/自定义文字/透明底 LOGO）→ 模式（四角/拉伸/平铺）→ 导出**。

### ⚠️ 历史提示（必须向用户说清）
REQ-022 F1 原链路「完稿转作品 → 加水印」环节**已在 2026-08-05 被用户拍板砍掉**（`REQ-022-B类低优先需求.md` L26）。当时的语境是**完稿转作品流程里自动加水印**。本需求是**独立手动工具**（画师主动加水印），与「流程自动联动」不是一回事——**用户 2026-08-07 已明确拍板：本需求做「全面版独立工具」**，方向确认。

### 画师使用场景（2026-08-07 用户拍板要点）
1. **画师能自己传透明底 LOGO**（PNG 带 alpha 通道）作为水印素材，与文字水印（画师名/自定义文字）并列可选
2. **多种水印模式**：至少包含**四角模式**（四角各一枚）与**单图拉伸模式**（水印图拉满全图/半透明铺底），建议再加平铺模式（重复排列覆盖全图）
3. **与现有图 / 新传图联动**——见下方可行性分析
4. 原图不动，导出的是新文件；支持批量（选多张同设置）

### 输入 / 输出
- 输入：
  - 图片来源 A（新传图）：拖入/粘贴本地图片（复用 ArtworkManage 上传交互）
  - 图片来源 B（现有图）：从「作品管理」选图（直接读 `/uploads/xxx` 路径，无需重新上传）或从订单完稿图（deliverables）选图
  - 水印素材：文字（画师名自动取 + 自定义）+ 透明底 PNG（画师上传，可保存复用）
  - 模式参数：四角 / 拉伸 / 平铺 + 位置/透明度/字号
- 输出：带水印的图片文件（下载，多张则打包 zip 或逐张下载）

### 📌 与现有图 / 新传图联动可行性（2026-08-07 四号核实）
**结论：不难，全部走前端 canvas 即可，后端零改动。**

| 联动方式 | 技术路线 | 难度 |
|---------|---------|------|
| 新传图 | 现有 `ArtworkManage.vue` 已有 `handleUpload`（el-upload 拖拽+粘贴），水印工具复用同一上传交互即可；本地 FileReader → canvas | 🟢 低 |
| 现有作品图 | `artworks.image_path` 存 `/uploads/xxx`，浏览器直接 `<img src>` + `canvas.drawImage`（**同源**，无跨域污染问题；`web` 与 `/uploads` 同域，由 fastifyStatic 托管，STATUS/REQ-030 已核实） | 🟢 低 |
| 订单完稿图 | `deliverables.file_path` 同样 `/uploads/` 同源，同一套 canvas 绘制 | 🟢 低 |
| 透明底 LOGO | 画师上传 PNG（读 alpha 通道），存画师级配置（`artist_watermark` 字段或独立表），水印工具与后续所有工具复用 | 🟢 低（新增 1 个上传端点或复用现有 upload） |
| 批量 | canvas 循环绘制 + 逐张下载 / JSZip 打包 | 🟡 中（JSZip 需引依赖，逐张下载免依赖） |

> **关键点**：所有图片处理都在浏览器本地 canvas 完成，图片不出本机，无服务器存储/带宽成本，天然符合零预算。唯一注意：canvas `toDataURL/toBlob` 对**非同源图片会污染画布**——本项目作品图/完稿图与后台同源，无此问题；若未来画师传外部 URL 图需先下载再处理（或提示不支持）。

### MVP 可拆
- MVP：新传图 + 文字水印（画师名/自定义 + 位置/透明度/字号）+ 四角/拉伸两种模式 + 预览 + 下载
- MVP+：透明底 LOGO 上传复用 + 平铺模式 + 现有作品图/完稿图直接选图联动
- P2：批量处理、水印预设保存（画师名+主页链接一键套用，主页链接快捷插入复用 F2 平台链接）、水印旋转角度

## 七、新想法⑥：节日关怀 vs 老客召回（单独分析）

### 现状核实（先摆事实）
| 维度 | 节日关怀 | 老客召回 |
|------|----------|----------|
| 触达渠道 | **REQ-028 消息网关（QQ Bot）已推迟**，无主动消息渠道；greeting_templates 是主页每日问候语（morning/afternoon/...），不是节日祝福 | **不需要外部渠道**——画师自己用 QQ 联系，系统只提供「该联系谁」的视图 |
| 数据基础 | 需要客户列表 + 渠道；客户列表本身还要先做 | **orders 表 client_qq 全在库**（必填），按 QQ 聚合历史订单/金额/最近一单即可 |
| 备案状态 | 无 | **FB-13 + REQ-031 C1 已备案**（回头客统计与客户标签） |
| 直接价值 | 情感维护，间接、难量化 | 复购召回，直接带来订单，可量化（召回 N 人→成交率） |
| 内容成本 | 节日文案模板（一次写好，复用） | 召回话术模板（一键复制「好久不见，最近还约稿吗」） |

### 分析
1. **节日关怀的瓶颈是渠道**：QQ Bot 推迟（REQ-028 §二 启动条件未满足），系统发不出去祝福。如果做，只能做成「模板库 + 复制」，画师手动发——价值大幅缩水，等于个文本模板功能。
2. **老客召回的数据全在库里**：orders 有 client_qq（必填）+ 时间 + 金额，纯聚合查询即可出「最近 N 天未下单的老客列表」。不需要新数据、不需要渠道、不需要迁移新表（查询现有表）。
3. **与②客户标记天然同源**：②要的「汇总行（共 N 单/累计金额/最近一单）」正是老客召回的判断依据。两个需求**共享同一查询 + 同一客户视图**，一起做省一半工。
4. 老客召回的落点：画师后台「工具」或「统计」下加**老客视图**：列表（QQ/昵称/共 N 单/累计金额/最近一单时间/N 天未下单）+ 筛选（超过 30/60/90 天未下单）+ 一键复制召回话术。**画师自己 QQ 联系**，不违反腾讯规则、无封号风险（REQ-028 §三 已警示高频群发风险）。

### 推荐：做老客召回，节日关怀后置
- **老客召回做**：数据现成、不依赖渠道、直接价值、与②合并省工、有备案支撑
- **节日关怀后置**：等 REQ-028 消息网关启动（启动条件见 REQ-028 §二：客户排队提醒兑现/画师要求 QQ 通知/平台需主动触达）再一起做，届时模板库 + 自动发送一步到位；现在做只能是个「复制文案」功能，不值当
- 若用户坚持节日关怀也要个轻量版：可做「节日文案模板库」（内置 20+ 节日文案，复制即用），约 0.5 天，但与工具类目「低频小工具」定位吻合，可作为 P3

### 工作量粗估（老客召回）
后端聚合查询端点 + 前端老客列表页（含筛选 + 复制话术）≈ **1~1.5 天**（与②共享客户视图，合并做约省 0.5 天）

### 拍板结论（2026-08-07 用户确认）
1. ✅ **做老客召回**，节日关怀后置（等 REQ-028 消息网关启动）
2. ✅ 老客召回与②客户标记**合并为同一批派工**（共享客户视图：标签+备注+汇总行+老客列表）

## 八B、时间条交互增强（2026-08-07 用户拍板）

### 用户原话（逐字）
> 「时间条功能要能按住日期那里可以左右滑动。而且设置两周时，不能直接截取两周，要可以前后滑动，两周只是缩放维度」

### 现状核实（2026-08-07 四号代码实测）
`QueueBoardCalendar.vue`（v0.25 D / v0.36 波1 / v0.42 Excel 式滚动）：
- 已有 2w/1m/3m/6m 四档缩放（`TL_ZOOMS`：14/30/90/182 天，dayWidth 48/32/12/7px）
- v0.42 已实现「画布覆盖订单实际日期范围，可左右滚动」（`tlCanvasStart/End` 取窗口与订单范围并集，上限 2000px）
- **缺失 1**：无「按住日期刻度区域拖拽平移」——只有原生滚动条/滚轮，用户期望按住日期区直接拖
- **缺失 2**：`TL_ZOOMS` 里 days 同时决定「视野宽度」和「画布裁剪」——2w 档窗口外订单虽有画布兜底，但「两周」被当作数据范围语义，用户期望「两周只是缩放（视野）维度」，前后滑动是常态

### 功能描述
1. **按住日期刻度区（顶部轴区/空白区）左右拖动 = 平移时间条画布**（类似地图拖拽/Excel 冻结窗格拖拽）；拖订单横条仍保持原有「改期」语义（不冲突——轴上拖=平移，条上拖=改期）
2. **缩放档位只是视野宽度**：选「两周」时，默认视野展示两周，但画布仍覆盖全部订单日期范围（含前后），**可以自由前后滑动查看窗口外的订单**——「两周」不等于「只看这两周」
3. 保留「回到今天」按钮（已实现 `tlGoToday`）；缩放切换不丢失当前视野中心

### 验收标准（草稿）
1. 当画师在时间条日期刻度区按住鼠标并左右拖动时，时间条画布应该跟随平移；松手后停留在新位置
2. 当画师选择「两周」缩放时，默认视野为两周，但当订单日期超出视野时，画布应该可以继续前后滑动查看超出部分（不被两周截断）
3. 当画师拖拽订单横条（非刻度区）时，应该仍然是「改期」操作，不应该触发画布平移
4. 当画师切换缩放档位时，时间条应该保持当前视野中心附近（不跳回今天，除非点了「回到今天」）

### 工作量粗估
纯前端（QueueBoardCalendar.vue 内部）≈ **1~1.5 天**（拖拽平移 pointer 事件 + 缩放/画布逻辑解耦；后端零改动）

### 待一号注意
- 拖拽平移与现有订单横条拖拽（`onTlBarDown`/`onTlHandleDown`）需事件区分（刻度区 vs 横条区），防冲突
- 平移实现注意 pointer capture / 防误触（轻移阈值）——**避免屎山，实现要优雅**（用户原话）
