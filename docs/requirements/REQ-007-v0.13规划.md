## R33：签名 URL 刷新机制

### 问题

签名 URL 有效期 15 分钟（`file-sign.js:8`，`FILE_TTL_MS = 15 * 60 * 1000`）。画师在订单详情页停留超过 15 分钟后：
- 参考图/交付文件/备注附图的签名过期 → 点击预览/下载返回 403
- 排期看板焦点图签名过期 → 图片变加载失败
- 客户在交付页等 QQ 通知后打开，签名可能已过期

### 需求描述

长停留页面的签名 URL 需要自动续期，不需要用户刷新页面。

### 验收标准

1. 当画师在订单详情页停留超过 15 分钟后，参考图/交付文件/备注附图应该仍然可以正常预览和下载，不出现 403
2. 当客户在交付页停留超过 15 分钟后，交付文件应该仍然可以下载
3. 当签名即将过期时（如剩余 2 分钟），前端应该静默刷新 URL，用户无感知
4. 当网络断开后恢复时，签名应该自动重新获取

### 技术方向（供三号参考）

- 方案 A：前端定时轮询——页面每 10 分钟调一次"刷新签名"接口，批量获取当前页面所有文件的最新签名 URL
- 方案 B：el-image 加载失败时自动重试——`@error` 回调触发重新请求订单数据（简单但体验有闪烁）
- 方案 C：后端签名 TTL 延长到 2 小时 + 前端 `@error` 兜底（最小改动，安全性略降）
- 建议：方案 A + B 结合——定时静默刷新为主，`@error` 兜底

### 风险提示

- 涉及所有使用签名 URL 的前端页面（OrderDetail/QueueBoard/DeliveryPage/OrderList），改动面广
- 刷新接口本身需要鉴权（不能公开），且需限流防滥用

## R34：Gallery/Folio/Atelier 模板外链展示

### 问题

R15（v0.12）给 Classic 模板加了外链展示（`socialLinks` + 自定义链接），但 Gallery/Folio/Atelier 三个模板**完全没有外链**（已验证：三个文件零匹配 `socialLinks`）。画师如果选了这三个模板，客户看不到任何社交链接。

### 需求描述

4 个模板统一支持外链展示。每个模板按自身布局风格放置（不要求位置一致，但功能一致）。

### 验收标准

1. 当画师设置了社交链接（微博/B站/自定义链接）时，Gallery 模板主页应该展示这些链接
2. 当画师设置了社交链接时，Folio 模板主页应该展示这些链接
3. 当画师设置了社交链接时，Atelier 模板主页应该展示这些链接
4. 当画师未设置任何链接时，三个模板不应该显示空白区域
5. 当画师切换模板时，外链内容不丢失（数据在 artists 表，与模板无关）

### 技术说明

- `useArtistData.js` 已提供 `socialLinks` composable，Classic 已在用——三个模板只需引入 + 按布局放置
- 纯前端，无迁移

## R35：login_codes.expires_at 已有库迁移

### 问题

P0-4 修复（`3e01ec1`）将 `login_codes.expires_at` 的 schema 声明从 DATETIME 改为 INTEGER（与实际存储的 Unix 毫秒一致）。但**已有数据库**的列类型仍是 DATETIME——SQLite 不强制类型，功能不受影响，但：
- 新库和旧库 schema 不一致，维护混乱
- 未来如果有工具/ORM 依赖列类型做推断，会出错

### 需求描述

v13 迁移脚本中统一处理已有库的列类型对齐。

### 验收标准

1. 当已有数据库执行 v13 迁移后，`login_codes.expires_at` 列类型应该与 schema 声明一致（INTEGER）
2. 当迁移执行后，现有登录码数据不丢失、不过期异常
3. 当全新部署时（无旧库），迁移应该幂等跳过

### 技术说明

- SQLite 不支持 `ALTER COLUMN`，需要重建表（CREATE 新表 → COPY → DROP → RENAME）
- 或：SQLite 类型亲和性下 DATETIME 和 INTEGER 行为一致，可评估是否值得做（建议：做，保持一致性）

## R36：嵌入白名单机制

### 问题

P0-5 修复后，嵌入页 CSP 收紧为 `frame-ancestors 'self'`（app.js:131-132），Settings.vue 嵌入区标注"暂未开放"。代码注释明确写了："未来画师自定义域名嵌入需配合白名单机制（P1-5 子域名方案落地后）"。

### 需求描述

画师能把自己的约稿主页/价格表嵌入到个人网站/博客。需要白名单机制控制哪些域名可以 iframe 嵌入。

### 验收标准

1. 当画师在设置中配置允许嵌入的域名时，该域名应该能 iframe 嵌入画师主页
2. 当未配置的域名尝试嵌入时，应该被 CSP 拒绝
3. 当画师未配置任何嵌入域名时，行为与现在一致（仅 'self'）
4. 当管理员需要全局控制嵌入功能开关时，应该有管理入口

### 依赖

- **P1-5 子域名方案**（待修复问题清单，开放）：子域名 vs 路径方案的决策直接影响嵌入白名单的实现方式
- 建议：P1-5 先定方案，R36 再实施。如果 P1-5 决定不做子域名，R36 的白名单逻辑会简化

### 待确认

- [ ] **C48**：P1-5 子域名方案的优先级？是否 v0.13 必须定？（建议：v0.13 定方案但不一定实施，R36 可延到 v0.14）

## R37：SRI / CSRF 防护

### 问题

P0-5 遗留（5c/5d）：
- **SRI**（Subresource Integrity）：前端静态资源（JS/CSS）无完整性校验，CDN 被篡改时可注入恶意代码
- **CSRF**（Cross-Site Request Forgery）：API 用 cookie 鉴权（`withCredentials: true`），但无 CSRF token 防护。当前 CORS 开发模式全开（`origin: true`），生产环境收紧后风险降低，但仍非零

### 需求描述

补齐 SRI 和 CSRF 防护。

### 验收标准

1. 当前端加载 JS/CSS 资源时，应该携带 integrity 属性（SRI hash），资源被篡改时浏览器拒绝加载
2. 当恶意网站尝试以用户 cookie 发起 API 请求时，应该被 CSRF 防护拦截
3. 当正常用户操作时，CSRF 防护不应该影响体验（无额外步骤）

### 技术方向（供三号参考）

- SRI：Vite 构建时生成 hash，注入 `<script integrity="sha384-...">`（vite-plugin-sri 或手动）
- CSRF：Fastify 的 `@fastify/csrf-protection` 插件 + 前端 axios 拦截器携带 token；或改用 SameSite=Strict cookie（更简单但需评估跨站场景）

### 待确认

- [ ] **C49**：生产环境 CORS 收紧后，CSRF 风险是否可接受用 SameSite cookie 替代 token？（建议：SameSite=Lax + 关键操作加 token 双重防护）
