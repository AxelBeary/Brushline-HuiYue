## R39：详情页状态流转重做（P0）

### 用户原声

> "详情页状态流转太差，只有'制作中'，下一轮必须安排。"

### 现状（已核实，OrderDetail.vue）

详情页有**两套并行的状态系统**：

**系统 A：固定状态条**（33-51 行）
```
el-steps: 待确认 → 已确认 → 制作中 → 已完成 → 已交付
```
- 5 个固定步骤，`wip`（制作中）一个状态兜底所有中间阶段
- 画师从"已确认"到"已完成"之间，无论经历草稿/线稿/上色/打回，客户和画师看到的都是"制作中"
- 操作按钮：确认/开始制作/打回/完成/交付/取消——全部基于固定状态

**系统 B：R30d 工作流卡片**（53-72 行）
```
OrderTimeline: 画师自定义节点（如 定稿→排期确认→草稿→线稿→上色→完稿→交付）
```
- 仅 `order.currentStageId != null` 时显示
- 有推进/打回按钮
- 老订单、关闭跟踪的订单看不到这个卡片

**问题**：
1. 两套系统同时显示时信息冗余且矛盾——上面说"制作中"，下面说"线稿阶段（4/7）"
2. 老订单/关闭跟踪的订单只有系统 A，"制作中"毫无信息量
3. 状态操作分散在两个卡片里，画师不知道用哪个
4. 用户说的"只有制作中"正是系统 A 的致命缺陷

### 需求描述

详情页的状态流转应该**以画师自定义工作流为主**，固定状态条退化为兜底。具体方向（供二号/三号定方案）：

1. **有工作流的订单**：工作流进度条成为主状态展示，固定 el-steps 隐藏或降级为辅助信息（如只显示"进行中"大类）
2. **无工作流的订单**（老订单/关闭跟踪）：固定状态条保留，但"制作中"阶段应该展示更多上下文（如最后操作时间、备注数、参考图数）
3. **操作统一**：推进/打回/取消等操作收敛到一个区域，不在两个卡片里各放一套
4. **取消订单**：保持滑块确认（R30e 已实现）

### 验收标准

1. 当订单接入了画师工作流时，详情页应该以工作流进度为主展示，画师能一眼看到"当前走到哪个节点、下一步是什么"
2. 当订单未接入工作流时，详情页应该仍然可用（固定状态条兜底），但"制作中"阶段不应只是一个词——至少显示最后活动时间
3. 当画师操作状态变更时，操作入口应该在一个地方，不需要在两个卡片之间找按钮
4. 当画师取消订单时，仍然通过滑块确认（不退化为普通弹窗）
5. 当客户查看进度页（track）时，看到的应该是工作流节点名（与 R30d 一致），不受详情页改版影响

### 依赖

- R30d 已合入（SPEC-002），后端 stage 推进/回退接口已就绪
- 本需求主要是**前端重构**（OrderDetail.vue 状态区重新设计），后端可能需微调（如老订单补充最后活动时间字段）

### 待确认

- [ ] **C52**：固定状态条是完全隐藏（有工作流时），还是缩小为辅助信息保留？（建议：隐藏——两套并行是混乱根源，有工作流就只看工作流）
- [ ] **C53**：无工作流的老订单，是否需要引导画师"启用工作流跟踪"？（建议：是，在状态区显示一个轻量提示"启用流程跟踪以获得更细粒度的进度管理"）

## R40：备注与状态流转展示合并（待确认）

### 用户原声

> "备注/备注记录和状态流转有必要合并吗？"

### 现状（已核实，OrderDetail.vue）

- **备注区**（126-164 行）：`order_notes` 表，自由文本 + 可选附图，按时间排列
- **状态流转**：`orders.status` + `orders.current_stage_id`，结构化状态变更
- 两者是完全不同的数据模型，分别展示在两个 el-card 中

### 四号分析

**数据层不应合并**：备注是自由文本（画师随手记），状态是结构化事件（系统驱动）。强行合并数据模型会破坏两者的语义。

**展示层可以合并**：做一个统一的"活动时间线"视图，把状态变更事件（"14:30 推进到线稿"）和备注（"14:35 客户说头发要蓝色"）按时间排列在一条时间线上。类似 GitHub Issue 的时间线——事件和评论混排，但数据类型不同。

### 四号建议

**做展示层合并，不做数据层合并。** 但工程量中等（需要后端提供统一的活动流接口，或前端合并两个数据源排序），建议排 P2，不阻塞 v0.14 核心功能。

### 待确认

- [ ] **C54**：用户是否接受"展示层合并"方案（时间线混排，数据结构不变）？还是用户想的是更简单的"把备注卡片移到状态卡片里面"？（建议：展示层合并——真正解决问题，且为未来 QQ 通知/客户可见时间线打基础）

## R41：备注附图支持拖拽上传（待确认）

### 用户原声

> "附图不能拖拽，有必要加吗？"

### 现状（已核实，OrderDetail.vue）

- **图库区**（103-118 行）：已有完整的拖拽上传（`ref-upload-tile`，dragover/dragleave/drop 事件）+ 点击上传 + Ctrl+V 粘贴
- **备注附图**（149-156 行）：只有一个 📷 按钮触发文件选择器，**无拖拽、无粘贴**

1. 拖拽上传是项目已有的交互模式（图库区、作品管理都有），备注附图不支持是**交互不一致**

3. 工程量小：复用 `usePasteUpload` composable + 在备注输入区加拖拽事件监听

### 验收标准（若确认做）

1. 当画师拖拽图片到备注输入区时，应该能直接上传为备注附图
2. 当画师在备注输入区 Ctrl+V 粘贴截图时，应该能直接上传为备注附图
3. 当拖拽/粘贴非图片文件时，应该给出提示（与图库区行为一致）
4. 当上传成功时，待发送附图预览应该正常显示（现有逻辑不变）

## R43：订单图库首次进入闪烁（Bug）

### 用户原声

> "订单管理首次进入图库闪烁。"

### 现状（已核实，OrderDetail.vue 74-124 行）

图库区 `el-image` 组件（88 行）：
```html
<el-image :src="reference.url" fit="cover" class="ref-img" @error="refreshNow" />
```

- `reference.url` 是签名 URL，由后端在 GET 订单详情时生成
- 页面首次加载时：HTML 先渲染 → 签名 URL 异步到达 → el-image 开始加载 → 图片显示
- 在"HTML 渲染"到"图片显示"之间，el-image 区域是**白色空白块**，多张图同时白闪
- 无 `placeholder` slot、无骨架屏、无 `loading="lazy"`

### 修复方向（供二号/五号参考）

1. **骨架屏**：el-image 的 `#placeholder` slot 加灰色骨架动画（Element Plus 原生支持）
2. **loading 属性**：加 `loading="lazy"` 让视口外图片延迟加载，减少首屏并发白闪
3. **背景色**：`.ref-img` 加 `background: var(--bg-secondary)` 让空白块不是纯白（最小改动）

### 验收标准

1. 当画师首次打开订单详情页时，图库区不应该出现明显的白色闪烁
2. 当图片正在加载时，应该有视觉占位（骨架屏/灰色背景），不是纯白
3. 当图片加载失败时，现有 `@error="refreshNow"` 刷新逻辑不受影响

### 工作量

15 分钟（el-image 加 placeholder slot + CSS 背景色）

## R44：焦点/放大逻辑互换

### 用户原声

> "焦点/放大逻辑互换：单击放大，小钩设焦点。"

### 现状（已核实，OrderDetail.vue 82-100 行）

```
当前交互：
- 单击图片 → selectFocusImage()（设为焦点图）
- 悬停 🔍 按钮 → openGalleryViewer()（放大预览）
- 焦点指示：✓ 角标
```

**问题**：单击图片=设焦点是低频操作（一个订单只设一次焦点），但占用了最通用的交互（点击）。放大预览是高频操作（画师反复看图确认细节），却藏在悬停按钮后面。

### 需求描述

互换两个交互：
- **单击图片 → 放大预览**（全屏 el-image-viewer，支持左右切换）
- **设焦点 → 通过 ✓ 小钩按钮**（悬停时显示，点击设为焦点）

### 验收标准

1. 当画师单击图库中的图片时，应该打开全屏预览（el-image-viewer），支持左右切换
2. 当画师悬停在图片上时，应该显示 ✓ 小钩按钮（设焦点）和 🔍 按钮（可删除，因为单击已等效）
3. 当画师点击 ✓ 小钩时，该图片应该被设为焦点图（现有 selectFocusImage 逻辑不变）
4. 当画师设焦点后，✓ 焦点指示标记应该仍然显示（现有 `.ref-focus-indicator` 不变）
5. 当画师在手机上操作时，单击放大应该正常工作（触屏无悬停，✓ 按钮需要常驻或长按触发）

### 待确认

- [ ] **C56**：手机端无悬停，✓ 设焦点按钮如何触发？（建议：手机端 ✓ 按钮常驻显示在图片角落，不依赖悬停）

### 工作量

30 分钟（交换 click 事件绑定 + 调整悬停按钮布局 + 手机端适配）

## R46：删除确认统一为滑块？（待确认）

### 用户原声

> "所有删除确认统一为滑块？"

### 现状（已核实）

| 操作 | 当前确认方式 | 位置 |
|------|-------------|------|
| 取消订单 | 滑块确认（R30e） | QueueBoard.vue |
| 删除作品 | ElMessageBox.confirm | ArtworkManage.vue:73 |
| 删除参考图 | ElMessageBox.confirm（推测） | OrderDetail.vue |
| 删除备注 | 无确认（直接删除） | OrderDetail.vue |

### 四号建议

**不统一。** 理由：

1. **滑块适合不可逆 + 高代价操作**：取消订单涉及客户、金额、排期，误操作代价极高。滑块增加摩擦是有意为之
2. **普通删除用标准确认即可**：删一张参考图/一个作品，误操作代价低（可重新上传），滑块会让日常操作变得繁琐
3. **批量删除例外**：多选删除（R45）一次删多张，误操作代价升高，**建议批量删除用滑块**

**总结**：保持分级——
- 单条删除：ElMessageBox.confirm（标准弹窗）
- 批量删除（≥3）：滑块确认
- 取消订单：滑块确认（已有）

### 待确认

- [ ] **C59**：用户是否接受分级方案（单条弹窗、批量+取消滑块）？还是坚持全部统一滑块？（建议：分级——全滑块会让"删一张图"变成"滑一下"，日常操作摩擦过大）

## R47：导航栏展开/折叠分组？（待确认）
