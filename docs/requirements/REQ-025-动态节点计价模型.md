## 一、用户原始场景（2026-08-04 口述，含一处已纠正的算术笔误）

> 收费节点：定金 10%、线稿 40%、细化 30%、完稿 20%。
> 客户下单 (100 原价 + 30 增项) × 1.5 倍率 = 195。画师改价成 300（所有节点没付过钱 → 每节点金额全部重算）。
> 收定金 30 确认，推进到草稿（定金节点完成，此后改价不再动定金节点）。
> 推进到线稿，收 150（累计 180，超过线稿节点价 120 → 线稿节点锁定，多付的 30 冲抵细化）。
> 细化待收自动 = 90 − 30 = 60。
> 临时加价 200：按未付节点的原始比例分摊 → 细化 90+120=210，完稿 60+80=140（用户原稿写 180，系 200×20/50 算错；守恒律验证：总价 500 − 已收 180 = 320 = 细化待收 180 + 完稿待收 140，故完稿必为 140）。
> 画师直接推进到完稿，待收 = 180 + 140 = 320，收齐，订单完成。
> 完稿后客户再加 50：所有节点不再变，系统提示额外收取 50。
> 收款允许负数（退款），退款只往后计不回溯。增项允许负数。除尾款外所有节点待收最低 0，尾款可为负（可退）。

**测试用例数值一律以本文档"边界案例"节的纠正值为准，不以用户原稿笔误值为准。**

## 二、核心规则（12 条，用户已确认）

### R1 总价条目化

订单应收总额 = 基础报价（档位价 + 增项 + 倍率 + 折扣的计价结果，即现有 quote_snapshot 语义）+ Σ 调整条目。
调整条目类型：`base`（初始报价）/ `manual_adjust`（手动改价）/ `extra_item`（需求增项）/ `discount_item`（优惠减项）/ `refund_item`（负增项）/ `extra_charge_after_close`（关单后额外应收）/ `extra_refund_after_close`（关单后额外应退）。
**条目只追加、不覆盖、不删除**（作废用新条目冲正）。

### R2 两个改价入口，底层统一条目化

- 入口 A：直接改总价（快捷方式）→ 系统自动生成一条 manual_adjust 条目（delta = 新总价 − 当前总价）
- 入口 B：加/减一笔（显式条目）
- **硬约束：订单发生过任何收款后，禁止无痕覆盖总价**（用户拍板 D2）——必须走条目

### R3 节点 = 比例 × 总价的快照

节点（收款分期）由画师工作流模板（名称、收款比例 basis_points、是否收款节点）在订单创建时生成快照。比例之和应为 100%（尾款节点可用"剩余比例"语义，与现有尾款基点逻辑衔接）。

### R4 锁价规则：完成 OR 付清，先到先锁（用户拍板 D1③）

- **完成即锁**：工作流推进越过该节点（该阶段工作完成）→ 节点价永久冻结
- **付清即锁**：该节点累计已分配收款 ≥ 节点价 → 节点价永久冻结（即使阶段未完成）
- 两者任一先发生即锁定，锁定后**任何增减价都不再改动该节点**
- **回退不解锁**：已锁定节点对应的阶段被要求返工（backStage），返工费按新条目处理，不回改已锁节点价
- 已锁未付清的差额为欠款，保留待收

### R5 增减价分摊公式

新增 delta（正或负）时：
1. 若订单已关闭（全部节点锁定且收齐）→ delta 计入额外应收（正）/额外应退（负），不修改任何节点（即用户"完稿后加 50"规则的推广）
2. 否则：delta 按**未锁节点的原始比例归一化**分摊：`节点新增 = delta × (节点原始比例 / 未锁节点原始比例之和)`

### R6 精度规则（守恒的前提）

**全程以分为单位**（现有 `_cents` 字段约定），分摊逐节点**向下取整**，**尾差归最后一个未锁节点**。保证 Σ节点价 + 额外项 ≡ 总价，无四舍五入误差。

### R7 收款顺序填充 + 超付抵扣

收款按节点顺序（定金→…→尾款）依次填充待收。当前节点填满后剩余金额**自动向后抵扣**下一未锁节点（即超付冲抵）。**不单独存储逐节点分配额**：已收/待收从订单级 paid_total_cents 按节点价顺序推导（实现细节见第五节）。

### R8 待收与下限

- 节点待收 = 节点价 − 已分配收款
- **非尾款节点待收最低为 0**
- **尾款节点待收可为负**（表示多收可退）

### R9 退款与负条目

- 收款允许负数（退款）；增项条目允许负数
- 退款/负 delta 只影响**未锁节点及之后**，不回溯已锁节点
- 退款分配顺序与 R7 镜像：先冲未锁节点，冲到底后尾款待收变负（应退）

### R10 订单关闭与额外应收/应退

全部节点锁定且收齐 → 订单关闭。此后任何增减价不进节点：正数 → 额外应收（PaymentBar 独立展示"额外待收 ¥X"）；负数 → 额外应退（提示应退，线下/人工处理）。

### R11 守恒断言（每次变动后必须成立）

1. 总价 = Σ 全部节点价 + 额外应收 − 额外应退
2. 总价 − 已收总额 = Σ 节点待收（尾款负值自然体现）
3. 任一节点：节点价 = 该节点基础分摊额 + Σ 历次分摊增量（条目可追溯）

计价引擎每次变动后自检，断言失败即拒绝该操作并报错（不允许带病记账）。

### R12 不留双轨

上线时全部订单切换新模型，演示数据随版本重建。**不做 legacy/dynamic 模式开关**（违反"开关默认关、统一模型"原则），不做历史订单迁移（上线前无真实数据）。

### R13 done = 半终态（2026-08-05 用户拍板，双向留痕）

**规则出典（用户场景原文）**：
1. "画完后客户想要多版本光影，画师额外收钱——退回修改太浪费操作"
2. "客户原本十张突然只要一张，画师想退一点"

**状态定义**：

| 状态 | 终态级别 | 价格变动能力 |
|------|---------|-------------|
| done（已完成，未交付） | **半终态** | 允许加钱/减钱/收款/退款，但必须条目化留痕 |
| delivered（已交付） | 完全终态 | 禁止一切价格变动 |
| cancelled（已取消） | 完全终态 | 禁止一切价格变动 |

**done 订单的操作白名单/黑名单**：

- ✅ 允许：加附加项（加钱）、负条目（减钱/退款）、收款、负数收款（退款）
- ❌ 禁止：无痕改总价（`updateFinalPrice` 对 done 关闭——改价必须走条目）、绕过条目直接删改价格结构、工作流回退（done 后打回上一节点无意义，返工需求用新条目表达）

**钱的去向由引擎自动判定（画师零决策）**：

- 客户**未付全** → delta（正或负）按 R5/R9 冲抵未付节点
- 客户**已付全** → 正数进 `extra_charge_after_close`（额外应收），负数进 `extra_refund_after_close`（额外应退），即 R10 语义

**实施时序（一号裁决 2026-08-05）**：done 订单当前唯一减价路径是 `updateFinalPrice`——负增项被 schema 拦死（`priceCents minimum: 0`），负收款只退钱不调总价。因此 **done 改价守卫必须与本需求第二阶段的负条目机制一起上线**，否则画师减价无门。五号价格守卫批（先行）只拦 delivered/cancelled，done 暂不拦。

## 三、边界案例（测试基准，数值已纠正）

**案例 1：用户主场景**（节点 10/40/30/20）

| 阶段 | 定金 | 线稿 | 细化 | 完稿 | 已收 | 待收合计 |
|------|-----:|-----:|-----:|-----:|-----:|-----:|
| 改价 300 后 | 30 | 120 | 90 | 60 | 0 | 300 |
| 收 30，定金锁 | ✅30 | 120 | 90 | 60 | 30 | 270 |
| 收 150（累计 180≥120），线稿锁，超付 30 冲细化 | 30 | ✅120 | 90（待收 60） | 60 | 180 | 120 |
| 加 200，摊未锁节点（30%:20%） | 30 | 120 | **210** | **140** | 180 | 320 |
| 推进完稿后收齐 | 30 | 120 | 210 | 140 | 500 | 0，订单关闭 |
| 关单后加 50 | 节点全部不变 | | | | | 额外应收 50 |

守恒：总价 500 = 30+120+210+140 ✓；500−180=320=180+140 ✓

**案例 2：完成但部分付款的节点**（线稿已完成只付 60，加 200）
线稿已完成 → 锁价，不参与分摊。200 摊细化 120、完稿 80。线稿欠 60 保留。

**案例 3：部分付款但未完成的节点**（线稿未完成只预收 60，加 200）
线稿未锁 → 参与分摊：线稿 +200×40/90≈88.88（分）、细化 +66.66、完稿 +44.44，尾差归完稿。

**案例 4：付清先于完成**（线稿未开画但客户预付全款 120，加 200）
线稿付清 → 先锁。200 摊细化/完稿，客户已付清的节点不再涨价。

**案例 5：关单后退款**（全部锁定收齐后 −50）
额外应退 50，节点不动。

**案例 6：尾差取整**（delta 200 元 = 20000 分，摊三个未锁节点 40:30:20）
20000×40/90=8888.88→取整 8888；20000×30/90=6666.67→取整 6666；20000×20/90=4444.44→取整 4444；合计 19998，尾差 2 分归最后一个未锁节点（20% 节点 → 4446）。断言 Σ = 20000。

**案例 7：回退不解锁**（细化已锁，客户不满意打回线稿阶段返工）
线稿/细化节点价不变；返工费 50 作为新条目摊给未锁节点（若无未锁节点则进额外应收）。

**案例 8：负增项把未锁节点冲到 0 以下**（总价减 200，未锁只剩细化 90 + 完稿 60）
细化、完稿待收最低 0，差额把尾款冲成负数（应退）。

**案例 9：done 状态的加减价**（R13 半终态，案例 1 订单收齐关闭后走到 done、尚未交付）

| 操作 | 节点（30/120/210/140） | 总价 | 条目 |
|------|----------------------|-----:|------|
| done 后加 50 | 全部不变 | 500→550 | `extra_charge_after_close` +50 |
| done 后减 200 | 全部不变 | 550→350 | `extra_refund_after_close` +200（退款线下执行，记负收款） |
| delivered 后任何加减价 | —— | —— | 全部拒绝（完全终态对照） |

守恒：550 = 30+120+210+140 + 额外应收 50 ✓；350 = 550 − 额外应退 200 ✓
与案例 1 末行的区别：案例 1 是"关闭（财务状态）"触发 R10；本案例是 **done 状态（工作流已完成、未交付）明确允许继续条目化操作**——画完后客户要多版本光影加钱、十张改一张退钱，都在 done 阶段完成，不需要退回修改（用户场景 ①②）。若 done 时客户尚未付全，加减价同样成立，客户应付随之同步更新，钱的去向由引擎自动判定（R13）。

## 四、验收标准

1. 当画师在订单创建后、任何收款前修改总价时，系统应该生成一条 manual_adjust 条目，所有未锁节点按 R5 重算且守恒断言通过
2. 当订单已发生收款时，改价入口应该只允许条目化操作，不提供无痕覆盖总价的途径
3. 当某节点被推进完成或已收满节点价时，该节点应该被锁定，此后的增减价不应该改变其节点价
4. 当已锁节点被工作流回退返工时，该节点价应该保持不变，返工费应该作为新条目分摊给未锁节点
5. 当订单加价且存在未锁节点时，增量应该按未锁节点原始比例归一化分摊，逐节点向下取整、尾差归最后一个未锁节点
6. 当客户付款超过当前节点待收时，超出部分应该自动抵扣后续未锁节点的待收
7. 当全部节点锁定且收齐后订单再加价时，节点应该全部不变，金额应该计入额外应收并在 PaymentBar 独立展示
8. 当发生退款（负收款）时，应该只影响未锁节点及之后，已锁节点与已收记录应该不变
9. 当非尾款节点待收被冲减时，待收应该不低于 0；当尾款节点被多收时，待收可以为负（显示应退）
10. 当计价引擎执行任何变动后，R11 三条守恒断言应该全部成立；断言失败时该变动应该被拒绝
11. 当 PaymentBar 展示时，客户/画师应该看到：已锁节点（锁定价）、当前节点待收、未来节点预估价、超付抵扣标签（如有）、额外应收（如有）
12. 当版本上线时，演示数据应该按新模型重建，系统内不存在新旧两套计价逻辑
13. 当订单处于 done 状态时，加钱/减钱/收款/退款应该全部允许且条目化留痕；无痕改总价、删改价格结构、工作流回退应该被拒绝；delivered/cancelled 状态应该拒绝一切价格变动（R13）

### 8.3 前端交互稿（文字描述）

**收款进度展示新要素**（验收标准 11）：

- **已锁节点**：显示锁定价 + 锁定标记，视觉上与未锁节点区分（不可再被分摊改动）
- **当前待收节点**：待收金额高亮强调
- **超付抵扣标签**：当某笔收款超出当前节点、抵扣了后续节点时，显示"已抵扣 ¥X"
- **额外应收/额外应退**：独立于节点条展示（"额外待收 ¥X" / "应退 ¥X"），对应 R10 关单后条目
- **订单级待收总横幅**（2026-08-05 用户补充）：顶部横幅显示「共待收 ¥X（当前节点：{name} ¥Y）→」——总额 = 总价 − 已收总额（含额外应收），避免画师前一节点漏收款时只看到当前节点一笔而误以为快收完了；点击跳转收款区
- ⚠️ 实施注意：现有 `PaymentBar.vue`（web/src/components/artist/）是**流程设置页的比例编辑器**（拖拽调百分比），与验收标准 11 说的**收款进度展示**（订单详情收款区 + 客户进度页）不是同一组件，改造对象是后者（现状：OrderDetail.vue 收款区 pool-nums + getOrderInstallments 推导展示）

**done 订单加减价操作入口布局**（R13）：

- 加钱：复用现有"附加工作项"入口（订单详情增项区），行为不变
- 减钱/退：新增"减价/退款条目"入口，与加增项同区域（金额为负的条目表单），文案明确"这笔钱会记入订单明细，客户可见"
- 无痕改价按钮：done 状态隐藏（前端）+ 后端拒绝兜底；delivered/cancelled 全禁
- 工作流回退按钮：done 状态隐藏

**错误提示文案**（示例，最终以 locales 规范为准）：

- 守恒断言失败："价格计算出现异常，本次操作已被拦截，请刷新页面后重试"（不泄露内部细节，附 requestId 供排查）
- 终态拦截："订单已交付/已取消，不能再修改价格"
- done 无痕改价拦截："订单已完成，请通过「加增项」或「减价/退款」调整价格，每笔调整都会留痕"
