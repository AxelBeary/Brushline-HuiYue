## 〇、人话总览（先看这段）

本方案定义**三处埋点**的完整口径：埋什么事件、什么时候触发、带什么数据、怎么防刷、怎么算指标。

- **换色率**：访客在客户端切换主色时记录一次（换了几号色）。
- **下单漏斗**：访客在下单页从第 1 步走到提交，每一步进入/离开/返回都记录，算哪一步流失最多。
- **后台功能使用率**：画师登录后台后，进了哪个页面、点了哪些关键操作（新建订单/改状态/设封面等），算各功能用得多不多。

三处共用一套埋点工具（`web/src/utils/track.js`，由二号批3先建骨架，本方案定义它后续接后端的规格）。埋点数据**不采集**：需求文本、参考图、QQ 号明文、订单号。

## 二、任务 1：换色率 `theme_accent_change` + 远程端点接入规格

### 2.1 换色埋点本身（已定义，本方案收录）

- **触发时机**：访客在客户端切换主色（`ThemePicker.vue` L32 `@click="themeStore.setAccent(a.id)"` 之后）。
- **事件名**：`theme_accent_change`
- **属性**：`accent`（1-5 的数字 id）、`palette_version`（`neon-v1` 旧五色 / `natural-v2` 换色后——OD-01 已拍板，`palette_version` 必须带上，否则"没人换色"无法区分"功能没用"还是"旧色太丑"，见第三方 9.2 必要性说明）。
- **时序铁律**（OD-01 拍板）：**埋点 ≤ 值替换同批上线**。若色值先换、埋点后加，中间的换色行为全部丢失。
- **骨架代码**（二号批3派工已给）：`trackEvent(name, payload = {})` 组装 `{ name, ts: Date.now(), version: EVENT_VERSION, ...payload }`，当前 `console.debug` 输出，`TODO(埋点后端)` 注释预留 `window.fetch('/api/events', ...)`。

### 2.2 远程端点接入规格（本批新增定义，**建议方案**）

> 以下为四号建议；**鉴权已拍板 B（匿名凭证）**，**端点路径、批量窗口两项仍待拍板**（见 §五 待拍板清单）。

**端点路径**：`POST /api/events`（与现有 `/api/*` 路由前缀一致；备选 `/api/tracking`）。按现有模式在 `server/src/features/` 下新建 `tracking/tracking.routes.js`，并在 `app.js` L255-263 区域 `app.register(import('./features/tracking/tracking.routes.js'))`。

**请求体**（批量上报，单次可含多条）：
```json
{
  "events": [
    {
      "name": "theme_accent_change",
      "ts": 1754550000000,
      "version": "natural-v2",
      "accent": "3",
      "anon_id": "a1b2c3...",
      "ua": "Mozilla/5.0 ..."
    }
  ]
}
```
- `name`：事件名（必填，白名单校验，防乱写）
- `ts`：毫秒时间戳（必填）
- `version`：当前调色板/应用版本（换色事件必填）
- `anon_id`：访客匿名标识（页面加载时生成，同一访客会话内保持一致，见 §3.3 会话串联）
- `artist_id`：画师事件才带（后台使用率，§4.3）
- `ua`：浏览器 UA（服务端可自行从 header 取，不必前端传——**建议服务端取，前端不传**，减体积）
- `ip`：服务端从请求取，前端**不传**

**响应**：`200 { ok: true }`；参数非法 `400`；超频 `429`（带 Retry-After）。

**鉴权**（**2026-08-07 用户拍板 B：访客行为需匿名凭证**）：访客事件（换色/下单漏斗）首次上报时需先取得**匿名凭证**（anon token），后续上报携带；画师事件（后台使用率）走现有登录会话或直接带 `artist_id`（画师是平台用户，非 PII，第三方 9.2 一致）。

**匿名凭证规格（anon token，拍板后定义，实施时三号细化）**：
- **获取**：前端首次需要上报时调 `POST /api/anon-token`（或首次上报时服务端 201 返回 token），服务端签发随机 token（建议 32 字节随机串，不可猜测）。
- **携带**：后续上报请求头 `Authorization: Bearer <token>`（或服务端种 cookie 自动携带，实施时二选一，建议 cookie 减少前端代码）。
- **存储**：`localStorage`（跨标签页共享——顺带解决 §3.3 会话串联的跨标签页问题）或 cookie；不用 `sessionStorage`（仅单标签页）。
- **生命周期**：建议 30 天滚动续期（A 测期间足够）；过期后前端静默重新获取，不打断访客。
- **兜底**：隐私模式/禁存凭证的访客（拿不到 token）→ 该次上报**限流 + 丢弃不入库**，不阻塞页面功能（埋点永远不得影响正常业务）。
- **隐私边界（重要）**：凭证是**匿名随机串**，不关联 QQ 号/订单号/需求文本；**不得**升级为"查询某访客下了哪些订单"的追踪标识——只用于统计去重、会话串联、限流。此边界写入实现验收。
- **其他用途（2026-08-07 用户问清后确认）**：① 换色率去重（"换过色的访客 ÷ 总访客"需稳定标识）；② 漏斗会话串联（跨刷新、跨标签页）；③ 按凭证精确限流（同 IP 多设备时比 IP 限流准）；④ 未来 A9 草稿恢复 / AB 分桶的现成基础（备案，不在本期实现）。

**批量策略**（**待拍板**，建议）：前端攒批——每 5 秒或攒满 10 条发一次（先到先发）；页面关闭/跳转时用 `navigator.sendBeacon('/api/events', ...)` 把剩余条数带走，避免关页丢数据。单请求上限 50 条（服务端校验）。

**数据落库**（实施时三号定，此处仅建议轮廓）：`events` 表（`id` / `name` / `ts` / `version` / `artist_id` 可空 / `anon_id` 可空 / `payload_json`）。建议不建索引之外的额外处理，A 测规模直接查表即可；如量级超标再考虑 TTL 清理（**保留期限待拍板**，建议 90 天）。

**与 Sentry 的分工**：Sentry = 错误监控（现状保留）；业务埋点 = 独立端点（`/api/events`），**不混用**。骨架注释已写明此分工，沿用。

### 2.3 换色埋点验收标准（可测试）

1. 打开任一客户端页面，依次点击 1-5 号主色各一次，Network 面板可见发往 `/api/events` 的请求（或控制台 `[track]` 输出——取决于是否已启用远程端点），无 4xx/5xx。
2. 请求体第一条事件：`name = 'theme_accent_change'`、`accent` = 当前所选 id（字符串 `'1'`-`'5'`）、`version` = 当前值版本（值替换后应为 `natural-v2`）。
3. 同一访客连续换 3 次色，3 条事件 `anon_id`（凭证关联的匿名标识）完全一致。
4. 服务端收到超限请求（如 1 秒内 50 次）返回 `429`，且超限部分**不落库**。
5. 请求体中**不出现**任何 QQ 号、订单号、需求文本字段。
6. **凭证流程**：首次上报前自动获取 anon token（`POST /api/anon-token` 或 201 返回），后续请求带 token；token 为不可猜测随机串。
7. **凭证兜底**：模拟禁存凭证（清掉 localStorage/cookie 后刷新），页面功能（换色/下单）**不受影响**，埋点请求被限流/丢弃但无前端报错。
8. **凭证隐私边界**：数据库/日志中凭证不与 QQ 号、订单号、需求文本建立任何关联（代码走查确认）。

## 三、任务 2：下单流程漏斗（正式定义）

### 3.1 步骤锚点（已按 OrderForm.vue 实测）

| 模式 | 步骤序列（key） | 总步数 |
|------|----------------|--------|
| 旧档位模式（无画风） | `tier`(选档位) → `detail`(写需求) → `contact`(联系方式) | 3 |
| 单画风模式 | `size`(选尺寸) → `addon`(增项+倍率) → `detail`(写需求) → `contact`(联系方式) | 4 |
| 多画风模式 | `style`(选画风) → `size`(选尺寸) → `addon`(增项+倍率) → `detail`(写需求) → `contact`(联系方式) | 5 |

- 下一步跳转：`@click="step = 2"`（L150 旧档位）、`step = addonStep`（L193）、`step = detailStep`（L316）、`goNextFromDetail()`（L627-643，写需求步→联系方式步，带空需求软提示）
- 上一步跳转：`@click="step = 1"`（L192）、`step = sizeStep`（L315）、`step = isStyleMode ? addonStep : 1`（L374）、`step = detailStep`（L415）
- 提交链路：`openReceipt()`（L713，校验+小票二次确认）→ `confirmSubmit()`（L738）→ `submit()`（useOrderForm composable）

### 3.2 事件定义（**命名已拍板 A：沿用第三方原名**，2026-08-07）

> 第三方 §9.2 的原始命名为 `order_form_step_view` / `order_form_step_back` / `order_form_abandon` / `order_submit_success`。批3派工举例 `order_step_enter`/`order_step_leave`/`order_step_back`（带"如"字，属举例非硬性）。**用户已拍板沿用第三方原名**（§9.2.1 决策判据表——OD-06/A9 阈值——引用原名，改名会与判据脱节；若将来想改短名须同步改判据引用，不可只改一半）。

| 事件名 | 触发时机 | 属性 | 用途 |
|--------|---------|------|------|
| `order_form_step_view` | 每次进入一个步骤（`step` 值变为 N 时） | `step_key`（tier/size/addon/style/detail/contact）、`step_index`（1 起）、`total_steps`（3/4/5）、`pricing_model`（style/legacy） | 到达率、各步流失率（OD-06） |
| `order_form_step_back` | 点击"上一步" | `from_step`（当前步序号）、`to_step`（返回目标序号） | 返回频次，揭示信息组织问题 |
| `order_form_abandon` | 离开下单页且未提交（路由离开 / 关闭标签页） | `last_step`（最后所在步序号）、`dwell_ms`（页面停留毫秒） | 放弃率（A9 草稿恢复决策） |
| `order_submit_success` | 提交成功（`showSuccess` 变 true） | `pricing_model`、`total_steps`、`elapsed_ms`（进入页面到提交成功） | 转化基线 |

可选补充（**待拍板**，默认不做）：`order_form_receipt_open`（小票二次确认打开）——可区分"走到提交但放弃"与"提交失败"，但增加埋点数，A 测样本小可不做。

### 3.3 会话串联与指标计算

**会话串联**：同一访客的一次下单流程，所有步骤事件必须能用 `anon_id` 串起来。**2026-08-07 拍板 B（匿名凭证）后，`anon_id` 由凭证体系提供**（§2.2）：token 存 `localStorage`/cookie，天然跨刷新、跨标签页共享，替代原 `sessionStorage` 方案（原方案仅单标签页）。

**指标定义**（以第三方 §9.2 口径为准）：

| 指标 | 计算方式 | 服务哪个决策 |
|------|---------|------------|
| 到达率 | 某步 `step_view` 次数 ÷ 表单会话数（anon_id 去重） | OD-06 步数是否压缩 |
| 流失率 | 1 −（下一步 `step_view` ÷ 本步 `step_view`） | OD-06：流失均匀→不压缩；集中在某 1-2 步→改那步；某步 >40%→该步单独重设计 |
| 停留时长 | 下一步 `step_view` 的 ts − 本步 `step_view` 的 ts（聚合看均值/中位数） | OD-06 信息组织 |
| 返回频次 | `step_back` 按 `from_step→to_step` 计数 | OD-06 回退揭示信息问题 |
| 放弃率 | `abandon` ÷ 表单会话数 | A9 草稿恢复：<15% 不做；15-30% 轻量版；>30% 完整版 |
| 转化基线 | `order_submit_success` ÷ 表单会话数 | 整体健康度 |

### 3.4 下单漏斗验收标准（可测试）

1. 旧档位模式完整走完 3 步并提交成功，服务端收到 4 条事件：`step_view`×3（`step_key` 依次 `tier→detail→contact`，`total_steps=3`）+ `submit_success`（`pricing_model=legacy`）。
2. 多画风模式完整走完，`step_view` 5 条（`style→size→addon→detail→contact`，`total_steps=5`）。
3. 在第 2 步点击"上一步"，服务端收到 `step_back`，`from_step=2`、`to_step=1`。
4. 填写到第 2 步后直接关闭/离开页面且未提交，服务端收到 `abandon`，`last_step=2`、`dwell_ms≥0`。
5. 同一访客的 4 类事件 `anon_id` 一致（跨刷新、跨标签页也一致——凭证存 localStorage/cookie）。
6. 提交成功事件的 `elapsed_ms` 为进入页面到提交成功的毫秒数，且 ≥0。

| `artist_page_enter` | 画师进入某个后台页面（路由变化） | `page`（路由 path，如 `/orders`）、可选 `referrer`（上一页 path） | 模块级使用率 |
| `artist_action` | 关键操作发生 | `action`（见下表）、可选关联上下文 | 只埋关键操作，不逐按钮 |

**关键操作清单（最小口径，共 6 类，暂不扩展）**：

| action 值 | 触发点 | 对应文件/行为 |
|-----------|--------|--------------|
| `order_create` | 手动录单提交成功 | `ManualOrder.vue` 提交 |
| `order_status_change` | 订单状态变更 | `OrderDetail.vue` 状态切换 |
| `artwork_set_cover` | 设封面（含取消） | `ArtworkManage.vue` 主图操作 |
| `artwork_publish` | 发布为作品 | `ArtworkManage.vue` / 订单发布入口 |
| `settings_save` | 设置页任一 Tab 保存成功 | `Settings.vue` 保存 |
| `guestbook_reply` | 留言回复 | `GuestbookManage.vue` 回复 |

> 说明：这 6 类是"改一单/发一图"级别的**有业务后果**操作。查询、翻页、展开折叠等浏览行为**一律不埋**——最小口径，避免过度埋点（四号落档提醒：用户主动要求此项，先定粗粒度，样本大了再细化）。

### 4.3 归属与属性

- 画师已登录（后台有登录守卫），事件**带 `artist_id`**（画师是平台用户，非 PII 问题，与第三方 9.2"每个事件带 user_id（画师）"一致）。
- 未登录访问后台（应被守卫拦掉），**不产生** `artist_page_enter`。

### 4.4 实施派工标注（给一号排期参考，非施工图）

- `artist_page_enter`：`ArtistLayout.vue` 是全局布局，路由变化统一收口——L221-227 已有 `activeMenu` computed 监听 `route.path`，可在 watch 路由处加埋点，一处覆盖全部页面。
- `artist_action`：6 个触发点分散在各视图文件，实施时逐个加 `trackEvent('artist_action', { action: 'order_status_change' })`。具体行号施工图由一号出。

### 4.5 后台使用率验收标准（可测试）

1. 画师登录后依次进入 仪表盘→订单管理→作品管理→设置，服务端收到 4 条 `artist_page_enter`，`page` 分别为 `/dashboard`、`/orders`、`/artworks`、`/settings`，且 `artist_id` = 当前画师 id。
2. 画师在订单详情把订单状态从"进行中"改为"已完成"，服务端收到 `artist_action`，`action='order_status_change'`。
3. 画师在作品管理点击"设为封面"，收到 `artist_action`，`action='artwork_set_cover'`。
4. 未登录直接访问 `/dashboard`（被守卫重定向到登录页），服务端**收不到**任何 `artist_page_enter`。
5. 同一画师同一天多次进出同一页面，`artist_page_enter` 按次累计（一次进入一条），不因 SPA 路由重复挂载而重复计数。
